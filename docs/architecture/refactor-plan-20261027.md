# BeefTV 重构方案：让每件事只有一个地方负责

状态：方案稿，待用户确认后按步骤派活。只含设计和排期，不含代码改动。
写于 2026-10-27，依据当前分支代码（`bb912a8b`）和近一个月提交记录。
相关文档：生成任务那条线的详细设计在 `docs/architecture/generation-task-state.md`（下称〔状态方案〕）；在途任务的排期在 `docs/architecture/refactor-coordination-20261027.md`。本文只讲重构本身，不再排其他任务。

## 一、结论

1. **问题多，主要原因是同一件事有好几个地方在管。** 不是代码写得不认真，而是改一处时，另外几处还在按旧的理解工作，于是「修好又漏」。
2. **不推倒重写。** 10 月 2 日那轮重构已经把 task、canvas、asset、generation 等领域从 `internal/app` 拆出去一部分，并有 `backend/internal/bootstrap/dependency_boundary_test.go` 守住依赖方向。这次是把没拆完、没删干净的部分收尾。
3. **分 6 步做，每步单独上线、单独回退。** 先删没人用的旧代码（最便宜、最快见效），再把生成任务、模型能力、画布保存这三块「多头管理」各收成一个负责人，最后才拆大文件。
4. **拆大文件放最后。** 大文件是结果不是原因；先把「谁负责」理清，文件自然会变小。只搬家不理清职责，等于把一个大文件拆成十个互相调用的小文件。

## 二、问题从哪来（用代码和提交记录说话）

近一个月主线有 270 个修复提交，按模块分：助手 42（另有 agent 13）、画布 35、视频 34（另有 Seedance 3）、生成 16、发布 12、更新器 10。集中在下面五个原因：

### 2.1 同一个事实，前后端各算一遍

| 事实 | 前端 | 后端 | 后果 |
| --- | --- | --- | --- |
| 生成任务提交了没有、扣没扣钱、结果入没入库 | 文件名含 generation/task/retry/recover/consumer 的约 79 个文件、1.47 万行 | `internal/app/task_*` 47 个文件 + `task`、`taskdelivery`、`taskbinding`、`taskruntime` 等包 | 节点锁死、重复扣费、取不回成片（详见〔状态方案〕第二节） |
| 模型支持哪些尺寸、时长、参考素材上限 | `web/src/lib/model-capabilities.ts`（1509 行），被 40 个文件引用 | `backend/internal/modelcatalog/capability.go`（1244 行） | 两边有同名函数 `isSeedance2Family`、`overlayOfficialSeedance2References`，规则要改两次；近一个月 Seedance 时长、参考素材数量、线路识别连修多次。前端 46 个文件、后端 36 个文件提到 Seedance |

### 2.2 不再使用的旧代码还在，修复时被一起改

前端曾经直接从浏览器调用模型渠道生成图片和视频，现在生成都走后端任务。但旧代码还在：

- `web/src/services/api/video.ts` 里的 `requestVideoGeneration`、`createVideoGenerationTask`、`pollVideoGenerationTask`，以及它们用到的 `video-provider-*.ts`（agnes、gemini、minimax、newapi、novita、openai、seedance，约 870 行）：除测试外没有任何调用方。
- `web/src/services/api/image.ts` 里的 `requestGeneration`、`requestEdit`：除测试外没有调用方。

后果：有人修渠道问题时会顺手改这些文件和它们的测试，看起来测试全绿，实际没修到用户在用的路径。

### 2.3 后端有一个「什么都管」的中心

- `backend/internal/app` 仍有 2.29 万行（不含测试），`app.Service` 上挂了 670 个方法，结构体里有十几把锁和各种协调器。
- 本该经过窄接口 `backend/internal/localapp/ports.go`（只有 7 个小接口、48 行）访问业务，实际上 `handler` 包有 45 个文件直接拿 `*app.Service`。项目约定写的是「handler → localapp/领域端口 → 实现」，现状没做到。
- 结果：一个接口背后改什么、会影响谁，只能读 `app` 的实现才知道；同一个 `/retry` 能走三种路径就是这么来的。

### 2.4 画布保存的入口太多

约 20 个前端文件直接涉及保存画布或处理画布版本号（包括 `project.tsx`、`use-canvas-keyboard.ts`、`assistant-canvas-save.ts`、`canvas-operation-journal.ts`、`director-viewport.tsx`、`canvas-drawing-storage.ts` 等）。谁先写、谁覆盖谁、冲突了谁重试，各处各写一套。#55「后台绑定改看画布版本号」、版本号对不上导致保存记录错乱，都是这个原因。

### 2.5 测试测函数，不测用户的一次操作

很多修复只给某个判断函数加了表格测试，没有「用户点击 → 后台 → 结果写回画布」的整条用例。#68 的 16 项组合检查 5 过 11 失败（来自 #83 的复查，见统筹文档第七节的核实说明）就是这样漏掉的。

## 三、重构后谁负责什么

原则只有一条：**一件事一个负责模块，其他地方只读它的结果，不自己推断。**

| 事情 | 唯一负责的地方 | 前端做什么 |
| --- | --- | --- |
| 生成任务状态、取回、重新生成、扣费 | 后端 task 领域（按〔状态方案〕给出 `task.outcome`） | 照着 `outcome` 显示和提供按钮，不再自己判断 |
| 模型能力（尺寸、时长、参考素材上限、支持哪些操作） | 后端 `modelcatalog` | 从接口读能力，表单按它限制；不再自带一份规则 |
| 渠道协议（请求怎么拼、响应怎么解析） | 后端 `generation` / `protocol` / `provider` | 不再拼渠道请求（插件与自定义渠道中转 `channel-transport.ts` 保留） |
| 画布文档保存与版本号 | 前端一个保存入口 + 后端 canvas 领域 | 其他模块提交「改动」给保存入口，不各自写库、不各自处理冲突 |
| HTTP 接口 | `handler` 只调用领域接口 | — |

和「本体轻量、其余做成拓展」的方向一致：本轮只理清本体里的职责，不搬剧本、导演台等功能到拓展（那是产品决定，另议）。

## 四、步骤

每一步：一个负责人；独立上线、独立回退；验收以用户的一次完整操作为单位。

### 第 0 步：删除没人用的旧代码（先做，风险最低）

- 删除 2.2 节列出的前端直连生成代码和只为它们存在的测试；删除前再用 `rg` 核一次调用方，`requestImageQuestion`、`requestToolResponse`（插件、导演台、审片在用）保留。
- 同类清理：凡是「除测试外没有调用方」的导出，一并列清单删除。
- 验收：`cd web && bun run build`、`bun run test` 通过；客户端里图片、视频、文本生成各跑一次免费或测试渠道。
- 预计：1 个任务，改动以删除为主。

### 第 1 步：生成任务线（已有方案，照做）

按〔状态方案〕第四节的 7 步执行，负责人是攻坚开发（统筹文档第六节已定）。本文不重复设计，只补一条：第 1 步 `Outcome` 落地后，前端那 79 个文件里凡是自己推断任务状态的地方，列一张「改为读 `outcome`」的清单，随第 6 步「删前端保护」一起删。

### 第 2 步：模型能力只留后端一份

- 先核实：后端现有目录接口（`modelcatalog` 的快照与 `capabilityConfig`）能不能覆盖前端 `model-capabilities.ts` 用到的全部字段。能覆盖就直接改前端读接口；缺字段就在后端补，不在前端补。
- 前端 `model-capabilities.ts` 收缩成「读取 + 显示」，删除前端那份 Seedance、Seedream 等型号规则。
- 验收：拿近一个月 Seedance/Seedream 的修复（时长下限、参考素材 12 个上限、Pro/Flash 识别等）各做一条前后端联合用例，结果与现在一致。
- 依赖：与第 1 步改的文件基本不重叠，可以并行。

### 第 3 步：画布保存收成一个入口

- 前端定一个保存入口（在现有 `local-workspace-repository.ts` / `canvas-operation-journal.ts` 基础上收，不另造），负责合并改动、版本号和冲突重试。
- 2.4 节那约 20 个文件改成「提交改动给保存入口」，删除各自的写库和冲突处理。
- 助手写画布、后台把成片写回画布，也走同一套版本号规则（后台那侧与〔状态方案〕第 2 步「取回循环写回画布」对齐，避免两处判断）。
- 验收：手动编辑、助手改画布、后台写回成片三者同时发生时，不丢改动、版本号连续；测试客户端按团队约定换 bundle id，不碰用户真实存储。
- 依赖：等第 1 步的第 2 小步（后台写回画布）定型后再做，避免同一处改两遍。

### 第 4 步：后端 handler 不再直接用 `app.Service`

- 按领域逐个把 handler 改为依赖 `localapp` 的窄接口；顺序按 `app` 里文件多少：task（47）→ provider（29）→ canvas（26）→ assistant（26）→ 其余。
- 每迁一个领域，把对应实现从 `internal/app` 移进领域包，并在 `dependency_boundary_test.go` 里把它加进「不能依赖 app」的名单（这是仓库已有的检查，不是新加的护栏）。
- 迁完后给 `handler` 也加同样的依赖检查。
- 验收：`cd backend && go test ./...`；每个领域迁移的 PR 不改行为，只搬位置和接口。

### 第 5 步：拆大文件（最后做）

前面理清职责后再拆：`web/src/pages/canvas/project.tsx`（3556 行）、`canvas-director-workbench.tsx`（2222）、`pages/assets/index.tsx`（2116）、后端 `repository/repository.go`（2317）、`generation/provider_error.go`（1607）。

拆法：按第三节的负责关系拆，每个新文件要能说清「它负责哪件事」；不允许把一个大 hook 拆成几个互相传参的小 hook 了事（10 月 2 日那轮「画布页面职责」已经吃过这个亏，`project.tsx` 至今仍 3556 行）。

## 五、今后开发怎么做才不乱

沿用统筹文档第五节的四条（一个事实一个来源、一个接口一种含义、验收按整条操作、一条线一个负责人），再补两条：

1. **加新路径的同一个 PR 里删掉旧路径。** 第 2.2 节的旧代码就是新路径上线时没删留下的。
2. **新功能动手前先说清它属于哪个模块。** 说不清就是还没设计好；属于剧本、导演视角这类的，优先做成拓展，不进本体。

不加额外的安全护栏和过滤；只保留已有的依赖方向检查和花钱、权限、防重复扣费这类业务规则。

## 六、排期与并行

| 顺序 | 步骤 | 能否与其他并行 |
| --- | --- | --- |
| 1 | 第 0 步 删旧代码 | 可以，立刻开始 |
| 2 | 第 1 步 生成任务线 | 已在进行，单独负责人 |
| 2 | 第 2 步 模型能力 | 与第 1 步并行 |
| 3 | 第 3 步 画布保存 | 等第 1 步的后台写回画布定型 |
| 3 | 第 4 步 handler 去 `app.Service` | task 领域等第 1 步完成后再迁；其他领域可先做 |
| 4 | 第 5 步 拆大文件 | 最后 |

发布：每一步都按 BeefTV 现有收尾流程走（独立检查 → 正式 PR → 交 Lucas review），不合进同一个大版本一次发。

## 七、需要确认的

1. 这份顺序是否同意；同意后先开第 0 步和第 2 步两个任务。
2. 第 2、3、4 步各派给谁（建议：方案先过架构师；第 0、4 步机械改动可交主力或 memoh；第 2、3 步跨前后端，交攻坚开发）。

## 八、本稿没有核实的地方

- 2.1 节「79 个文件」是按文件名关键词统计，其中有些只是显示用，不一定都在推断任务状态；精确清单在第 1 步里出。
- 第 2 步假设后端目录接口基本能覆盖前端用到的能力字段，没有逐字段比对。能推翻的证据：前端用到的字段在后端快照里没有来源。
- 2.4 节「约 20 个文件」是按保存和版本号相关函数名搜索，没有逐个确认每个文件都真的写库。
- 修复提交按 `fix(scope)` 统计，scope 写得不规范的提交可能被算错模块。
