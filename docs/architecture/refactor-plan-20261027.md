## 一、结论与本次范围

**继续已有重构，先补生成任务第 3 步的完整请求行为；不从第 1 步重写，不先做全仓删除或保存架构替换。**

PR #269 的 `Outcome`、图片自动恢复及既有交付器已经在 main；PR #275 的剪辑修复也在 main。保留这些实现和测试。#269 尚未实现本轮扣费原值、视频/图片完整扣费查询，不能仅凭“第 1、2 步已合入”把旧方案里挂在第 2 步的全部目标判为完成；这些差额现在明确交给第 3 步。

#83 的 16 项检查是对 #68 `e08b6bea` 的研究反例，5 过、11 失败；临时扣费补丁只让六项映射从 2 过变成 6 过。两者均不是当前主线或新方案已经通过验收。本轮核对了原报告、JSON 记录和相关代码，没有重跑实验、启动客户端或调用付费接口。

允许的交付仅是本文、统筹记录和状态方案的修订。不修改产品、测试、数据库、依赖和发布证据，不关闭原任务，不恢复 #52、#75、BeefAPI #31，不把新功能纳入 v2.0.5。发布补验继续由独立任务负责。

## 二、原稿判断中哪些成立，哪些需要收回

### 2.1 生成任务有具体重复和信息丢失，不能用文件数代替职责分析

当前 main 的 `backend/internal/app/task_outcome.go` 仍只组装图片回执与派发事实；`task/outcome.go` 有 `ConfirmedUncharged` 布尔输入和 `unrecoverable → confirm` 分支。#68 分支已加扣费日志读取，但把多种原值压成布尔值，又没有限定本轮身份。#83 的反例解释了为何局部修复仍会漏掉结果。

真正需改的是操作接纳、恢复和扣费事实之间的交接，不是所有名字带 task/generation 的文件。原稿“79 个文件、约 1.47 万行”只是关键词规模统计，撤销其作为迁移清单的作用。后续第 6 步只改实际作出业务判断的调用点；进度绘制、订阅、资源下载和 UI 临时状态不因文件名相近而迁移。

### 2.2 旧前端生成函数是删除候选，不是全仓清理授权

本轮在 `web/src` 搜索确认：`api/video.ts` 的 `requestVideoGeneration/createVideoGenerationTask/pollVideoGenerationTask` 仅有模块内相互调用；`api/image.ts` 的 `requestGeneration/requestEdit` 没有检出的产品调用。这个结果只证明静态名称搜索未找到调用，尚未证明所有动态导入、重导出和对外扩展合同都可删除。

同文件的 `requestImageQuestion` 被导演台、剪辑助手使用；`requestToolResponse` 被 `plugin-host.ts` 和审片调用。视频文件还导出存储 helper 和类型，不能整文件删。`channel-transport.ts` 与插件能力也保留。撤销“所有除测试外没有调用方的导出一并删除”的计划，限定为上述五个函数及经过引用核实的私有依赖。

### 2.3 模型能力已有服务端投影，但还不能宣称字段完全等价

核对了 `web/src/lib/model-capabilities.ts`、`backend/internal/modelcatalog/types.go`、`capability.go`、`catalog.go`、`channel_admin.go`：后端已发布 `capabilityConfig`，前端 `modelCapabilityConfigFor` 会合并保存配置、默认值与官方型号覆盖。迁移要处理这个优先级，不能只是把导入换成接口读取。

| 已比对字段组 | 当前事实 | 后续如何处理 |
| --- | --- | --- |
| 图片 `references/size/quality/transparentBackground/responseFormat/outputFormat/maxOutputs/fixedOutputs/generationOutputs` | 前后端类型均有；`size.presets` 均有尺寸字段 | 选一个已保存型号对比实际目录 JSON、表单选择和后端接纳，不以类型同名证明值相同 |
| 视频 `references/duration/durationSupported/ratios/resolutions/operations` 及默认值、音频/水印开关 | 前后端类型均有；含 UTF-16 提示词上限、分数时长和音频最低时长 | 先验证 Seedance 的 4 秒输出、2 秒参考音频和现有参考素材限制，再移除对应前端覆盖 |
| 文本 `streaming/references` | 两侧都有；缺省值仍需实际目录验证 | 保留现有行为，不能把缺字段解释成不支持 |
| 文本 `thinking` | 前端类型有，后端 `TextCapabilityConfig` 没有同名字段 | 明确反例：不能声称目录已覆盖全部前端能力；先查实际消费和来源，再决定补投影或保留本地展示判断 |
| 音频 | 后端 `normalizedChannelModelCapability` 返回 nil，另有 `audioOptions` | 不把音频强塞进文本/图片/视频合同；不借本轮重新做费用估算 |
| 新建/未保存 BYOK、缺缓存配置 | 前端仍依赖 `defaultModelCapabilityConfig` 及本地工作流参数 | 保持可配置能力；在来源未覆盖前不删除兜底，不要求远端目录在线才能编辑 |

以上是类型与调用链的静态比对，不是所有型号/每个字段值的全量运行核验。原稿“后端基本覆盖，缺字段就全部补后端”改为按实际消费逐项决定。

### 2.4 画布已经有共用保存入口

| 调用或模块 | 本轮读到的责任 | 不能据此推出什么 |
| --- | --- | --- |
| `project.tsx → use-canvas-project-lifecycle.ts` | 编辑完成调用保存，后者到 `syncLocalCanvasProjectToBackend` | 页面出现保存函数不等于自建冲突算法 |
| `assistant-canvas-save.ts` | 先 flush，再调同一同步入口，并确认未保存编辑 | 不能把它删成“重复保存系统” |
| `local-workspace-repository.ts` | 已有 `syncLocalCanvasProject`、`persistCanvasDocument`、合并/冲突处理；`persistCanvasTimeline` 复用文档保存 | 不需要先新造一个总保存器 |
| `canvas-operation-journal.ts` | 保存本地操作身份、预期版本与在途请求 | 操作记录不是另一份后端画布文档 |
| `lib/canvas/canvas-drawing-storage.ts` | 画板快照、草稿与绘制资源，使用独立 drawing API | 它的 revision 不自动等于主画布文档 revision，不能混成一个对象 |
| 后端任务绑定 | 成片写回与 revision 更新属于后端事务；#55 改的是失败绑定的再次尝试条件 | #55 不是前端保存重构，也不能证明其他保存路径均有问题 |

原稿“约 20 个文件各自写库、各自冲突重试”没有逐项证据，本轮撤回。只安排查明实际绕开共用入口的写入或可重现的丢改动场景；找不到反例就保留当前实现，不按文件数量改造。

### 2.5 handler 仍依赖 app，但已拆出的领域不应再搬一次

`localapp/ports.go` 已有窄端口；handler 仍直接引用 `app.Service`，后续可以按一个完整操作缩小依赖。`bootstrap/dependency_boundary_test.go` 已覆盖 task、generation、modelcatalog、operations、canvas、taskdelivery、taskbinding 等领域。原稿“每迁一个领域都搬实现再加名单”会重复已有工作，撤销。

app 保留必要的跨领域编排。只有已经确定责任、且能减少依赖的实现才迁移；不以文件数安排 task → provider → canvas → assistant，不建立只转发整套 Service 方法的新接口。

### B：生成任务第 3 步，按 3A → 3B → 3C 继续

以[状态方案 3.11](generation-task-state.md#311-第-3-步专项调整先固定操作再执行和投影)为唯一详细说明。从实施时的 main 出发，对照 #68 逐项保留正确实现，不能整包复制它或 #83 的实验补丁。

| 顺序 | 改动与保留 | 必须能证明的结果 |
| --- | --- | --- |
| 3A 操作接纳和免费入口 | 复用 `AgentOpRecord`、SQLite 接纳事务、现有恢复租约/交付器；所有带编号 `/retry` 保存动作与原轮次；免费不写付费同意 | 首次、并发、恢复完成后重放、数据库重开、接纳后中断均不新生成；回执轮次不丢；原任务仍有恢复路径 |
| 3B 本轮扣费原值 | 保留字段缺失/空值/确定值和派发身份；投影不再从跨轮日志推断；保留 #68 有效协议解析 | 六种映射、换渠道/新轮、迟到结果、真实 DTO 信封、查询失败不抹已存结算；图片相对 `result_url` 第二次读取及 BaseURL 带 `/v1` |
| 3C 查询与交付 | 自动/人工共用恢复；合法查询 POST 保留，结果下载失败只重试交付；结果期限与链接期限分开 | 两种暂停、临时下载失败、明确过期、未知期限、pending 后退款、超分与 RunningHub 查询；本地任务与轮次不变 |

`3A/3B/3C` 是第 3 步内部顺序，不是三次半成品发布。新正式实现需重放 #83 的 16 项夹具并补其未测时序与公开 HTTP 入口；不以实验绿灯代替实现验收。BeefAPI #31 的资金结算改法仍暂停：现有查询协议与假响应可支持客户端实现，真实两端共同验证须待上游另行恢复并交付，不能把它变成“重做第 2 步”的先决条件。

### C：三个范围受限的整理候选

1. **模型能力先做一条已保存模型路径。** 逐字段记录后端返回、前端选择、提交值、默认值与用户覆盖。无差异后才删该型号的重复规则；文本 thinking、音频和未保存 BYOK 暂保留既有来源。发现行为差异先列清，不擅自改变用户可选项。
2. **旧生成代码清理单独做。** 限 2.2 的五个候选函数及确认专用的依赖；检查直接/别名/重导出/动态引用及插件合同，迁移仍有业务价值的协议测试后再删除旧入口测试。验证前端构建、相邻测试和免费任务入口，不要求真实付费生成。不将其排为生成任务修复的前置工作。
3. **画布保存先验证现有合同。** 手动编辑、助手写入、后台成片绑定共同发生时，沿现有入口测试版本与改动保留。发现具体绕路或冲突后才修对应调用；画板内容与主画布文档仍分开保存。不得因旧“20 个文件”清单批量改造。

这些工作可在文件范围明确后安排，不再假定“基本不重叠”。#81/#82 在做用户可见文字，#75 留有费用代码；准备实施时先比较实际 diff，不恢复它们，也不覆盖其改动。

### D：稳定后缩小 handler 依赖，再处理大文件

生成任务第 3 步稳定后，从一次任务请求的 handler → app 编排 → task/repository 选择一个真实需要的端口。只缩小调用面，不一并改任务行为和收费规则。已有依赖检查照常使用；只有引入新的依赖问题才补对应检查，不扩大为全仓框架。

大文件最后按真实责任拆分。拆分必须减少业务判断的重复或隔离一项稳定能力；只减少行数、把参数转传到更多 hook 的改动不安排。具体文件和工期以当时的变更为准，不沿用原稿行数预算。

### E：第 4–7 步仍按原迁移条件推进

第 3 步完成不等于费用预览、付费同意与拒绝守门已经完成。第 4 步观察期 → 第 5 步执行拒绝 → 第 6 步前端读 Outcome、删旧推断 → 第 7 步清理，顺序保持。收费规则启用后不能通过关闭守门回退。

#75 的简化估价是展示用途，未知不作零、超分预扣不计最终合计；不实施 #64 的复杂费用方案。后续收费提交用的报价与同意属于原状态方案第 4–5 步，不能把展示缓存当成付费授权，也不能借这条依赖恢复 #75。
