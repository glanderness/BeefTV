## 一、结论

1. **不需要把所有任务停下来，只需要冻结「生成任务取回 / 重新生成 / 扣费」这一条线上的零散补丁。** 这条线上现在有 5 个以上任务各改一块，互相改同样的文件，而且连续几轮「修好又漏」，是目前问题最集中的地方。其余任务（文档站、思考过程显示、剪辑、BYOK、费用估算、协议升级）和它改的文件基本不重叠，继续做。
2. **原因就是你猜的那个：职责不清。** 「上游收没收到、扣没扣钱、结果有没有入库」这三件事，现在前端约 30 个文件、后端约 18 个文件各自推断一遍（〔状态方案〕第二节）。后台一个 `/retry` 接口里有三种走法，前端事先不知道走哪条，只能猜；猜错就表现为节点锁死、重复扣费、取不回成片。
3. **不另写一份新的大重构方案。** 〔状态方案〕已经是这条线的整体设计，#83 又指出它第 3 步有漏洞，并给了第 3.11 节的调整。统筹要做的是：把它定为唯一方案、给所有相关任务一个先后顺序、说明每个任务是「并入」「保留」还是「继续独立」。
4. **发布规则：v2.0.5 只带已通过完整检查、且不依赖第 3 步以后的内容。** 取回 / 扣费路径上不再往 v2.0.5 塞新补丁。

## 二、为什么说是职责不清（用最近的改动对照）

| 现象 | 背后的同一原因 |
| --- | --- |
| #15 上游成功、画布拉不到成片，节点锁死 | 前端自己写 `resourceReloadAvailable`、`generationSubmissionState`，后台不知道 |
| #16 / #263 来回修自动取回 | 前端扫描 + 后台 `/retry` 两处各有一套取回逻辑 |
| #68 补第 3 步，最新实现 16 项组合检查 5 过 11 失败（#83） | 免费回执约定冲突、扣费原值丢失、恢复职责分散；局部测试没跑完整操作，所以漏了 |
| #55 后台绑定重试逐字段比对改成看画布版本号 | 重试的触发条件由多处各自判断 |
| BeefAPI #30/#31 图片结果与扣费不一致 | 客户端把「结果请求失败」当成「没有结算事实」；`billing_state` 缺失和显式空值被混为一谈 |

共同点：**同一个事实有多个推断者；一个接口多种含义；测试只测单个函数，不测从用户点击到结果入库的整条操作。** 补一处就会在另一处漏，所以会反复。

## 四、收拢后的实施顺序

沿用〔状态方案〕第四节的 7 步，不另起一套。按下面的依赖排：

1. **第 1 步 `Outcome` 纯函数 + 表格测试**：无依赖，先做；表格里加入 #83 的 16 项组合和 #30 第 7 节的响应样例。
2. **第 2 步 后台自动取回 + 读 BeefAPI 扣费结论**：依赖 BeefAPI #31 的响应字段；客户端要处理 `result_url` 相对地址、`billing_state` 缺失与空值的区别、结果请求失败时保留已存结算。
3. **第 3 步 `/recover` + 同编号重放**：按 #83 的 3.11 重做，验收以完整操作（点击到入库）为单位，不接受只有局部函数测试的通过。
4. **第 4 步以后**：第 4 步观察期必须在第 6 步删前端保护之前完成；第 5 步守门改拒绝后不能靠关守门回退（方案第四节已写明）。

每一步：独立上线、独立回退、各自带「两端联合验证」，BeefAPI 与 BeefTV 的共同验证只用免费路径。

## 五、今后开发的约定（只留四条，不加额外护栏）

1. **一个事实一个来源。** 提交状态、扣费结论、结果是否入库，只有后台算，前端只读；前端不再写 `resourceReloadAvailable` 之类的推断字段。
2. **一个接口一种含义。** 免费取回和扣费重跑分开接口；新增接口前先确认不会让已有接口多一种走法。
3. **验收以整条操作为单位。** 凡涉及取回 / 重新生成 / 扣费的改动，必须有从用户点击到结果入库（或明确失败）的组合用例，不能只测单个判断函数。
4. **同一条线同一时间一个负责人。** 取回 / 扣费线的改动都挂到〔状态方案〕的某一步，不再另开补丁任务；发现新问题先补进该步的验收表。
