# canvas.bind 终态恢复测量（2026-10-27）

## 结论

- 已换任务或已删除节点的绑定失败会在首次发现后写入 `recovery_outcome` 私有标记；节点状态未变化时，后续扫描不再调用 `canvas.task.bind`。
- 节点重新指回原任务、或按原节点 ID 重建后，后台会重新尝试绑定并清除标记。
- 在本机数据副本上跑 120 秒，`canvas.bind` 尝试从基线 **258 次**降到 **58 次**，减少 **77.5%**；修改后的 58 次集中在首次发现，之后没有新增绑定尝试。
- CPU 没有出现同幅度下降：基线约 **5.58%**，修改后约 **5.40%**，相对下降约 **3.2%**。这说明本改动主要消除重复绑定、事务和诊断日志；全量任务扫描、结果投影等其他后台工作仍在运行，不能据此宣称整体空闲耗电已解决。

## 方法

- 数据：从本机 BeefTV SQLite 工作区通过 SQLite backup 复制出独立数据库；没有打开真实工作区写入者。测试 data directory 为空，未配置 BeefAPI 连接、凭据或上游请求。
- 运行：构建当前 backend 测试二进制，在独立副本上每 5 秒执行一次 64 条批次的成功任务绑定恢复，持续 120 秒。
- 基线：使用同一代码和同一副本规模，但每轮都直接执行绑定，不读取或写入新的终态标记，等价于修复前的重复扫描行为。
- 绑定计数：统计本地 support trace 中 `canvas.bind` 的 start 事件，并用副本中的节点状态核对为已换任务/已删除节点的绑定目标；不统计真实上游生成或付费调用。
- CPU：使用 `/usr/bin/time -p` 统计测试进程的 user + sys 时间除以 wall time；这是进程级平均值，不是系统功耗或 WebView 主线程帧率。

## 原始结果

| 运行 | wall | user | sys | 平均 CPU | `canvas.bind` start | 唯一任务/节点目标 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 基线 | 126.21 s | 5.76 s | 1.28 s | 5.58% | 258 | 58 |
| 当前实现 | 125.00 s | 5.66 s | 1.09 s | 5.40% | 58 | 58 |

基线事件从测试开始后持续约 116 秒出现；当前实现的 58 个事件集中在第一次发现这些终态目标，随后约 100 秒没有新的 `canvas.bind` 事件。

## 边界与未测项目

- 没有启动旧前端、桌面发布包或真实用户工作区；没有做真实画面绘制验收。
- 没有做真实上游生成、扣费、退款或 PostgreSQL 测试。
- 这次只解决确定性绑定失败的无限重试；扫描器仍会按既有游标遍历成功任务，成功绑定的其他路径和全量扫描成本没有在本改动中重构。
- 120 秒单次本机测量会受 SQLite 缓存、进程调度和副本内容影响；CPU 差异应视为“基本持平”，不能当成稳定性能承诺。
