# Mac 画布卡顿、闪烁、丢节点：v2.0.4 实测与优化建议（2026-10-27）

## 结论

- **拖动节点：已经好了。** v2.0.4 上拖动节点稳定在 57–60 fps。PR #241 的改动已随 #247 合进 main，#241 可以关掉。
- **平移画布：还卡。** 300 节点画布上 3 轮中位数是 40 fps，最慢的帧要 100–200 ms。主要开销是两件事：一是平移时页面反复挂载、卸载节点，React 每 4 秒要把整个画布页面重渲染 72–100 次；二是 WebKit 绘制毛玻璃（backdrop-filter）、SVG 连线和图片的成本。
- **缩放：还卡。** 约 40–44 fps。关掉毛玻璃、连线、图片、阴影，基本不改善，所以卡在 React 和 LOD 切换，不在绘制。
- **播放视频时拖动：** 视频播放时拖节点是 59.8 fps，已经不卡。视频播放时平移画布是 44 fps，但同一块画布不播视频时平移也只有 32 fps，所以平移慢不是视频造成的。
- **丢节点：没复现。** 反复测试后，300 个节点、144 条连线全部还在。但发现了一个会让节点“跳一下”的问题：打开画布时，小于最小尺寸的视频节点会被自动放大，并以中心为准挪位置，而且会写回文档（见第 4 节）。
- **闪烁：没直接看到。** 这一轮没有录屏逐帧核对。可疑来源列在第 4 节。
- **后台 canvas.bind 循环：** 后台每 5 秒扫一遍所有已成功的任务，一遍遍尝试把结果绑回节点，每分钟约 130 次失败。它在 Go 后台运行，不卡画面，但持续耗电、写日志（见第 5 节）。属于“节点任务回填”，按约束等 #25 一起改。

### 2.2 逐层关掉的对比（perf300，每项 3 轮中位数）

| 关掉的层 | 平移 fps / p95 / >50 ms 帧 | 缩放 fps / p95 / >50 ms 帧 |
|---|---|---|
| 不关（基线） | 40.2 / 58 / 17 | 40.3 / 66 / 22 |
| 毛玻璃（backdrop-filter） | 54.3 / 37 / 5 | 43.1 / 63 / 18 |
| 连线（SVG） | 57.1 / 33 / 3 | 44.3 / 62 / 17 |
| 图片和视频（隐藏） | 51.4 / 41 / 5 | 44.0 / 62 / 20 |

结论：
- 平移的绘制成本主要在毛玻璃、连线、图片三层，单关任意一层都能明显改善，全关就接近满帧。
- 缩放全关后仍是 42 fps，问题不在绘制，而在缩放过程中 React 提交视口、LOD 卡片和 DOM 卡片来回切换（缩放时 `img` 从 14 个变成 0 个又变回来）。

这块画布只有 25 个节点，平移却比 300 节点的还慢，而且页面渲染次数更多（每 4 秒约 100 次）。原因是 20% 缩放下不少节点卡在 LOD 阈值附近，平移过程中频繁有卡片挂载或卸载。视频播放没有让拖动或平移变得更差。

另外看到一个现象：视频播放时，用无障碍接口读窗口要 5–9 秒，平时不到 1 秒，说明主线程比较忙。这一点没有单独量化。

## 4. 打开画布时节点被自动改尺寸（会让人觉得“闪了一下”或“节点跑了”）

- 现象：perf300 打开后，84 个视频节点（每份 7 个）从 270×480 变成 420×746.7，位置统一挪了 (-75, -133)，并且写回了文档（perf300 写入时 revision 是 1，测完是 6，期间没有手动编辑它）。真实数据库里还有 3 块画布含有小于最小尺寸的图片或视频节点，下次打开同样会被改。
- 原因：`use-canvas-project-lifecycle.ts:49` 打开画布时调用 `resetInterruptedGeneration`，它对每个节点执行 `ensureMediaNodeMinimumSize`（`canvas-project-generation.ts:621` → `canvas-node-size.ts:69`）。只要节点宽小于 420 或高小于 236，就放大并以中心为准重新定位，不管节点里有没有内容、用户有没有手动调过尺寸。
- 影响：打开画布时卡片先按旧尺寸画出来，下一帧突然变大、移位，旁边的节点可能被盖住。
- 改法：只对空节点或生成中的占位节点补最小尺寸；有内容的节点不动，或者只在显示层套最小外框、不写回文档。改 `canvas-node-size.ts` 和 `canvas-project-generation.ts`，约 10–20 行加测试。这个函数挂在“中断生成恢复”路径上，和 #25 的回填重构挨得很近，改之前先和 #25 对一下。

## 5. 后台 canvas.bind 循环（node_task_mismatch）

**谁在调用：** 不是前端，是 Go 后台。调用链如下：

1. `startGenerationDeliveryRecovery`（`backend/internal/app/task_delivery.go:121`）每 5 秒触发一次 `RecoverIncompleteGenerationDeliveries`。
2. 它调用 `recoverPendingCanvasBindings`（`task_binding.go:75`），用游标分批扫描，每批 64 个任务。
3. `SucceededTasksForDelivery`（`repository/task_delivery.go:69`）的条件只有“状态成功、结果不为空”，不排除已经绑定过或者已经确定绑不上的任务。
4. 对每个任务调用 `recoverCanvasTaskBindings` → `executeCanvasTaskBind`，执行 `canvas.task.bind`。

**为什么一直失败：** 节点后来重新生成过，`metadata.taskId` 换成了新任务（或者节点已删除），`canvas/task_bind.go:84` 就返回 `node_task_mismatch` 或 `node_deleted`。`skippableCanvasBindError` 把这个错误当成“跳过”吞掉，但没有记下“这个任务已经确定绑不上”。所以扫完一圈从头再来，同一个任务大约每 25 秒重试一次，永远不会结束。

**规模：**
- 用户真实数据（v2.0.3）：10-27 00:19–01:25 的 66 分钟里失败 8,603 次（8,455 次 node_task_mismatch，148 次 node_deleted），覆盖 5 块画布、21 个节点。
- v2.0.4 加同一份数据：平均每分钟 133 次。按每天开 8 小时算，约 6.4 万次；全天开着约 19 万次。
- 每次绑定都要开一个数据库事务，读任务、读产物、读并解析整块画布 JSON，再往诊断日志 `events.jsonl` 写 2 行。真实数据 66 分钟写了 8 MB；`coverage.json` 显示 10-22 以来因为超量丢掉了 145 万条诊断事件。
- 已经成功过的绑定每轮也要重放一次。重放时插入操作记录会撞上唯一约束，GORM 把这当错误打一行日志（v2.0.4 一小时约 2,300 行）。

**对卡顿和耗电的影响：**
- 卡顿：基本没有。它在 Go 后台运行，不占 WebView 主线程；循环一直在跑时，空闲帧率仍是 58–60 fps。
- 耗电：有。v2.0.4 空闲 120 秒，带这份数据时 CPU 用了 13.5 秒（约一个核的 11%）；空数据目录只用了 3.3 秒（约 2.7%）。多出来的约 8% 基本来自这类后台恢复，其中这个循环占大头，但没有把它和其他恢复单独拆开测。用户正在用的 2.0.3 进程运行 39 小时累计 CPU 278 分钟，平均约 11.8% 个核，和测得的一致。频繁的事务也会和画布保存抢 SQLite 写锁，这一点没测。

**改法**（属于节点任务回填，按约束这一轮不动，建议并进 #25 的重构步骤）：

1. 对 `node_task_mismatch`、`node_deleted`、`canvas_mismatch` 这类确定绑不上的结果，记一个终态（例如在操作记录里存 `skipped` 和当时的节点任务 id）。下次扫描时排除，节点的 taskId 变化后才重新尝试。改 `app/task_binding.go`、`repository/task_delivery.go`，约 60–120 行加测试。
2. 扫描只取还有待绑定意向的任务，不再遍历所有成功任务。
3. 已知会跳过的结果不再写诊断日志。重放路径插入操作记录改用冲突时忽略，不再打错误日志（`operations/store.go:112`）。约 10–20 行。

和 PR #265 的关系：#265 改的是前端助手和 `operations/canvas_node_configure.go`，不碰这几个文件，不会冲突；但和 #25 是同一块业务。

## 7. 为什么 Windows 好一些（推断，未验证）

Mac 端已经量到的两类开销：
1. WebKit（WKWebView）合成毛玻璃、SVG 渐变连线和大量图层的成本：关掉之后平移从 40 提升到 59 fps；
2. 平移和缩放中 React 页面级重渲染和 DOM 增删。

第 2 类在 Windows 上同样存在。Windows 用的是 WebView2（Chromium），GPU 光栅化和 backdrop-filter 的实现不同，第 1 类成本大概率更低；PR #250 的说明里，Windows 探针包在 80/512 节点下全部通过，也是旁证。要确认这一点，需要在 Windows 上打同一个探针补丁、用同一份 perf300 素材跑同样的场景。这一轮没有 Windows 机器，所以没做。

## 9. 复现方式

1. 在 v2.0.4 代码上应用 `docs/reports/2026-10-27-mac-canvas-perf-probe.patch`。
2. 执行 `bun run build:desktop`，把 `web/dist` 复制到 `backend/cmd/desktop/frontend/dist`。
3. 执行 `CGO_LDFLAGS="-framework UniformTypeIdentifiers" go build -tags desktop,production`，用生成的二进制替换发布包里的 `Contents/MacOS/BeefTV`，重新签名。
4. 用 `--data-dir=<数据副本>` 启动，副本里先删掉 BeefAPI 连接和模型配置。
5. 窗口保持在最前面，按右下角的 `perf-*`、`tog-*`、`batch-ablate` 按钮跑测试。
