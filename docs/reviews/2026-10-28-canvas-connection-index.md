## 需要修正的发现

### P2：索引的严格矩形相交漏掉原来接受的吸附圆边缘

位置：候选 `web/src/lib/canvas/canvas-connection-target.ts:62`，以及已有 `canvas-spatial-index.ts` 中的 `intersects`。

旧判定是 `dx * dx + dy * dy <= radius * radius`，圆周也接受。新代码先用未扩大的节点矩形和指针周围矩形查询索引；已有空间索引故意只接受严格相交，矩形相切就丢弃节点。节点没有进入候选列表，后面的圆形判定无法补救。

最小复现：目标图片左上角 `(1000, 0)`、尺寸 `320 × 180`，从另一个图片的输出端拖线，100% 缩放、指针在 `(944, 90)`，恰好位于左输入端外侧 56 像素。结果如下，普通和批量拖线均复现：

| 返回或最终动作 | 基线 | 候选 |
| --- | --- | --- |
| `nodeId` | `target` | `null` |
| `isNearNode` | `true` | `false` |
| 松手后 | 连成线 | 打开创建菜单 |

后果来自真实 `finishConnection` 的分支：有目标则连接，只有 `isNearNode` 则取消，其余打开创建菜单。批量拖线也按这个标志决定是否创建节点。该位置在节点外，依靠 window 的松手处理；不能用“端口自己的 pointerup 会直接连接”消除这条回归。

证据：

- [differential.json](2026-10-28-canvas-connection-index/differential.json)：2740 次定向差分中有 15 个精确相切差异，其余取样未发现差异。覆盖普通/批量、正向/反向、多个缩放；反向批量不适用的组合返回空，没有冒称覆盖。
- [hook-browser.json](2026-10-28-canvas-connection-index/hook-browser.json)：36 条真实前后 `useCanvasConnectionController` 路径，用浏览器分发 `PointerEvent`，经过 rAF、状态更新和松手分支。100% 下距离 55、56、57 像素分别检查；56 像素时普通和批量均从“连接”变为“创建菜单”。
- 这是无头 Chromium 的 hook 复放，未渲染实际画布、媒体与世界层；AntD 消息和插件持久化被替身隔离。没有把它写成原生鼠标、完整客户端或 FPS 验收。

最小修正方向：让连线专用索引的粗筛选包含圆周可能命中的节点，再保留原有精确圆形判定。不要直接修改共享空间索引的严格相交规则，现有裁剪等调用有意依赖该规则。补精确左右边缘、缩放和跨网格位置的普通/批量回归，并验证 `isNearNode` 及最终菜单分支。

### P2：原报告不足以证明用户场景收益，且误判了可达输入

位置：作者 `docs/performance/2026-10-28-canvas-interaction.md` 的结论、复现与限制；`web/scripts/canvas-interaction-bench.ts:146`、`:183`。

以下修正会直接影响“保留还是撤回”的判断：

1. **末尾背板有现成入口。** `use-canvas-node-operations.ts:288` 的 `createStoryboardGroup` 和 `:339` 的 `createReferenceGroup`，对已有图片/视频设置 `parentId`，再把新 frame 追加到数组末尾。`project.tsx:3108`、`:3109` 已接到多选工具栏。无需先重排 `nodes`，`isNodeHiddenByCollapsedFrame` 便会逐子节点找到末尾背板。作者人工构造的“末尾批次根”不因此自动得到可达性证明，但不能把背板和批次根一起排除。
2. **作者只测了热查询。** `measure` 先预热，再反复使用同一 `nodes`；首次索引建立已经被排除。标题、进度、尺寸等更新换数组后的重建也没测。作者报告里的速度比只能用于这条热路径。
3. **差分不是 5000 节点覆盖。** `parity` 的规模固定为 `[100, 300, 500]`，不受 `--nodes 5000` 控制。5400 次是全部夹具、规模、缩放的总数；只调用普通 resolver，没有调用批量 resolver。随机平面取样不能代替精确圆周、滚动分镜与节点更新场景。
4. **测量顺序不是逐样本交替。** 每一场景先完成整个 `legacy: measure(...)`，再完成整个 `current: measure(...)`。同进程能减少一些差异，仍不能据此认定并发机器负载不影响比值。本次补测按样本交替前后顺序。
5. **原有浏览器测试没有经过新落点入口。** `canvas-connection-drag.browser.test.ts` 验证已有连线在节点拖动预览时的曲线更新，夹具调用 `applyCanvasNodeDragPreview`；它未导入这次的控制器或 resolver。它通过不能证明新拉线落点与松手保持一致。

因此搁置任务材料中沿用的“最坏根节点顺序不可达”判断：代码证明至少末尾背板可达。也不采纳作者报告中“300 节点三条路径都不是主因”的整体排除结论：本轮能够验证的只有局部逻辑，缺少完整桌面事件、页面更新和绘制证据。这些是证据解释修正，没有扩大产品规则或授权范围。

原作者脚本也已独立复放，见[author-replay.json](2026-10-28-canvas-connection-index/author-replay.json)：`--nodes 300 --entries 60 --repeats 60`，取得 5400 次差分、0 差异。这个结果与本文发现可以同时成立：它没有定向覆盖本文失败输入。原作者测量可复放，不代表原报告对覆盖范围和真实收益的所有解释成立。

独立取样覆盖：文档顺序靠后的合法节点优先、上层不合法仍寻找下层、源自身的靠近标志、已有连线、背板/批次折叠与展开、脚本行/上下文和滚动位置、批量表参考列、正反向端口、多个缩放、移动后的新旧位置、重新排序和零尺寸节点。除精确相切外未发现差异。这是有限取样，不是所有输入等价证明，也未改变既有“文档顺序”选择为“视觉叠放顺序”。

缓存按 `CanvasNodeData[]` 身份存于模块级 `WeakMap`。当前核对的 `project.tsx:233` 的 setter、`use-canvas-node-editor.ts` 的改名/尺寸/展开、`use-canvas-generation.ts:243` 的任务回填，均通过新数组传入；没有发现这些入口把已索引数组中的坐标就地修改后继续复用旧键。数组换新后查询使用新数据，配置、连线、脚本滚动也在每次查询时读取。WeakMap 本身不要求显式释放旧数组，也没有另建一套持久业务状态；未做堆快照，因此不宣称已经排除所有内存问题。

**正确失效不等于失效便宜。** 仅变更非几何数据也会重建全部索引。本次以实际 `updateCanvasNode` 给 300 节点中的一个节点更新 `taskProgress`，数组换新后查询读取其余 299 节点的 `position` 共 1196 次；同数组的热查询为 0 次。实际生成回填的 `canvasGenerationTaskNodes` 也使用 `nodes.map` 返回新数组。这项重建由下一次查询惰性触发，**不是每次进度更新都立刻建立索引**；停止拖线期间的多次更新可以只在下次查询建一次。不能把它说成陈旧索引缺陷，也不能把热查询当作稳定只读附近节点的完整成本。

## 计入建立与更新后的性能

本次新增[独立测量](2026-10-28-canvas-connection-index/independent-bench.json)，直接调用固定候选和自动提取的旧回调。普通网格、批次根在前、背板在前，以及从真实创建分镜组回调产生的末尾背板，分别计时。每个样本交替前后执行顺序，保留中位数和 p95。

`first-query` 包含首次建索引及查询；`progress-update`、`title-update`、`geometry-update` 包含真实 `updateCanvasNode` 的局部修改及随后查询；`60-query-drag` 包含首次建立和总共 60 次查询；另测每 15 次查询换一份进度数组，共建立四份索引。批量补测还包括真实 `planBatchConnections` 与源资格检查，但不含 DOM、React 和绘制。这些数值是同机 Bun 的逻辑成本，**不是完整拖线墙钟时长或 FPS**。

以下为中位数，单位毫秒，每格“旧 → 新”。“分镜组 N”是给 N 个已有节点中的 N−1 张图片创建分镜组，实际数组再多一个末尾 frame；其创建方式来自产品回调。

| 场景 | 热查询 | 首次建立并查询 | 更新单节点进度并查询 |
| --- | --- | --- | --- |
| 普通 300 | 0.0128 → 0.0038 | 0.0130 → 0.0325 | 0.0165 → 0.0348 |
| 普通 1000 | 0.0511 → 0.0102 | 0.0498 → 0.1055 | 0.0593 → 0.1135 |
| 普通 5000 | 0.2121 → 0.0476 | 0.2035 → 0.5344 | 0.2506 → 0.5677 |
| 分镜组 300 | 0.3150 → 0.0064 | 0.3029 → 0.0400 | 0.3228 → 0.0421 |
| 分镜组 1000 | 3.3393 → 0.0194 | 3.2515 → 0.1263 | 3.4649 → 0.1660 |
| 分镜组 5000 | 92.6336 → 0.1029 | 91.5413 → 0.7509 | 97.9598 → 0.7835 |

普通 300 节点每次热查询约省 0.009 毫秒，首次或更新后一次查询反而多约 0.02 毫秒。这支持“函数更快”，不能单独支持“用户感觉不再卡”。连续 60 次、计入首次建立的查询总 CPU 时间为 `0.774 → 0.245` 毫秒；若期间每 15 次更新进度，则为 `0.780 → 0.341` 毫秒，收益仍很小。

真实分镜组改变了判断：1000 节点首次查询从 `3.251 → 0.126` 毫秒，更新进度并查询从 `3.465 → 0.166` 毫秒，60 次查询含三次中途进度更新的总 CPU 时间从 `203.177 → 1.732` 毫秒。5000 节点分组的旧查询约 90 毫秒量级，超出常见一帧预算；该输入经产品代码可构造，不能仅当作无法到达的人工最坏排列。不过本次没有在完整客户端创建并拖动这一规模。

批量拖线加上 20 个源的真实规划和资格检查后，普通 1000 节点约 `0.251 → 0.221` 毫秒，分镜组 1000 节点约 `3.120 → 0.222` 毫秒；普通画布的整段逻辑收益明显小于单看 resolver 的倍数。源节点多时剩余规划和 `find` 仍会占成本，本次没有新提批量算法重构。

标题、几何更新和其余场景共 128 组统计均在 JSON 中。不能用“索引永远只访问附近节点”描述首次建立或更新；也无需在这个候选里立刻增加第二种几何版本状态。已有共享空间索引得到复用，普通/批量规则通过回调共用，没有证据要求扩大结构重构。

测量环境和负载见[environment.json](2026-10-28-canvas-connection-index/environment.json)、[measurement-load.json](2026-10-28-canvas-connection-index/measurement-load.json)。1000/5000 分镜组的 60 次查询场景仅 12 组配对样本以控制成本，其 p95 不作可靠尾延迟结论。该规模通过产品入口的代码可达性不等于用户当前工程正有这么多节点。

### P2，报告解释：总耗时再加建立耗时会重复

位置：作者 `docs/performance/2026-10-28-canvas-interaction.md:247`，第 5.6.3 节 `索引合计耗时` 一行。

本轮候选两个计时起点已移到回调体开头。执行顺序是：回调开始计时 → 坐标换算 → 调用 resolver → 必要时建立索引 → query → 策略判断 → 回调结束计时。**建立耗时已经包含在 `after.落点总耗时` 内。** 报告同时写“整个回调计时”和“总耗时再加建立”，后一条公式与实际执行矛盾。

本轮没有只手填计数后比较公共统计函数。脚本从**完整应用后的控制器逐字提取两个回调体**，提供宿主 ref 和坐标函数后直接调用；实际几何、可见性、策略与空间索引仍运行。只为检查累计关系，将坐标换算设为 7 毫秒、真实索引建立和 query 分别附加 3 / 1 毫秒假时钟。计数字段从 0 开始，均由实际插桩代码写入。

普通和批量有效命中都得到同一关系：

| 单次调用 | `落点调用` | `落点总耗时` | `索引建立耗时` | `索引查询耗时` |
| --- | --- | --- | --- | --- |
| before 第一次 | 1 | 7 | 0 | 0 |
| before 同数组再次 | 1 | 7 | 0 | 0 |
| after 第一次 | 1 | **11** | 3 | 1 |
| after 同数组再次 | 1 | **8** | 0 | 1 |

after 两次累计是回调总计 **19**、建立 **3**、查询 **2**。正确分解为 `19 = 坐标 14 + 建立 3 + 查询 2`；按报告错误公式会得到 `19 + 3 = 22`。第一次同样会从真实的 11 错读成 14。表中时间是人为成本，**不是性能测量、不是优化速度比较**，仅用于证明范围及累计关系。

两侧批量无源出口也各计 1 次。该输入下基线在源解析后提前返回，候选会先坐标换算再在 resolver 内返回，因此假时钟分别为 0 / 7；这是原有执行顺序不同，不是漏计或多计，不能要求无效源输入两侧耗时相等。

正式采样应按以下方式读取：

- **完整落点回调总成本：直接比较 `before.落点总耗时` 与 `after.落点总耗时`。** 若调用数不同，分别保留调用数和整段总量，按既定同路径条件解释，不能单凭总耗时差认定加速。

- `落点总耗时` 仍不是整个拖线事件、React 提交或绘制耗时；这些范围不能混为一个数字。

3. **整窗统计混入大量无落点调用的帧。** 例如 2000 档两侧仅约 4% 的帧有落点；1000 after 第 1 段仅 2.91%。因此“小规模整窗平均约 60 fps”可保留，但不能由此证明活动拖线时没有停顿，也不能拿长度不同的整窗 p95 证明相同手势的尾延迟改善。
4. `gt33` 实际统计 **`>33.4 ms`**，不是严格的 `>33 ms`。4000 档对应 `47/432=10.88%`、`47/411=11.44%`、`10/506=1.98%`；这些比例可以由汇总复算，但缺逐帧原件，不能确认长帧与落点调用、保存或窗口前置是否重叠。rAF 间隔也不是屏幕真实呈现帧或 GPU 绘制耗时。
5. “每次耗时”是**整个记录段的累计耗时 / 调用数**，混合移动与松手回调，不是单次中位数或 p95。两侧 `dropTargetMs` 直接比较，索引建立/查询仍只是内部拆分，不再加到总量上。原件中的毫秒字段全部为整数，零值只能按当前计时/汇总分辨率解释，不能当成零成本；本轮没有校准 WKWebView 时钟。

### 3. 1000 档有重复 start，不能认定完整窗口

`perf-after-grouped1000-r2.ndjson` 原第 6–8 行为：

```text
2026-10-28T14:23:19 start recording
2026-10-28T14:23:24 start recording
2026-10-28T14:23:29 stop  帧=334 fps=60.0 … 落点调用=32 落点总耗时=6
```

这与作者第 5.7.3 节“改后本轮全部 20 次录制都只有一条 start”矛盾。探针的开始按钮每执行一次会 `reset()`；若第二条来自真正的第二次按钮事件，前段统计就被清除。334 帧对应约 5.57 秒，与最后一次 start 较接近，但这仍不能单凭秒级接收时间证明实际重置。

**必须区分按钮事件与 HTTP 重传。** `perf-sink.py` 只接收 GET 并写文件，不会执行浏览器的 `reset()`；HTTP 请求重传本身不能清零前端计数。因此作者“HTTP/1.0 重发造成中途清零”的因果解释尚未成立。本轮初次协调中曾把这一段直接称为“被重置”，读取接收端后已向 Chief 更正为“重复 start，完整窗口未证明”。

处理：保留原件及 `6/32=0.1875 ms` 这段汇总算术，**撤下它作为完整三次手势、首次建立或正式 FPS 对照的资格**。作者若能找到有前端事件序号/时间的原始记录，可以据此澄清；现有材料不能恢复被疑似截掉的前段，不能补造。

### 4. 同一布局不等于同一输入与状态

1000/2000/4000 档可见卡片中心集合大致一致，301 档两侧集合也彼此相同，但位置不同于另外三档。这支持局部布局相近，不能证明完整画布、视口、连线与输入相同：

- `perf-ports` 从 DOM 顺序取前两个卡片，不记录实际拖拽所用节点。4000 before r1 显示 `nodeA=perf-child-65`、`nodeB=perf-child-64`，after 显示相反顺序；报告解释实际拖拽始终从左到右，这是作者描述，**ndjson 没有输入事件可独立确认**。不能仅凭这两个字段认定拖反，也不能仅凭中心集合排除输入差异。
- 4000 档的种子本来就有 `perf-child-64 → perf-child-65`：种子以偶数节点连到下一个奇数节点。控制器对已有连接仍会更新锚点、生成新的连接数组；新连接还会调用节点关联更新。因此即使确实从左向右拖，也不能默认每次都是新建连线。采样没有保存每次拖拽前后的连接数、具体边、锚点和节点数组身份。
- after 的 `indexBuild=1 / 2 ms` **只证明记录段累计建立一次并记为 2 ms**。计数没有时间戳，探针 `reset()` 清计数而不清产品的 WeakMap 索引缓存，回调在未录制时也能建立索引。它可能是首次建立，也可能是节点数组改变后的重建；1000 after 两段 `indexBuild=0` 明确是没有在记录段中量到建立。不能据此认定“提交后重建只花 2 ms”，更不能证明持续生成时反复重建均无可见停顿。
- 作者记录的不同 load、前置窗口、缓存重置、引导关闭与编辑历史都可能改变状态。“除连线外源码相同，所以差异只能是环境噪声”过强：**源码相同不意味着执行状态、输入、缓存和错误路径相同**。

### 5. 保存 400 的影响：不能说与交互无关，也不必丢弃所有回调读数

固定树缺访问日志、请求与响应正文、错误 `reason/code/retryable`、操作日记和采样期间的 revision 读回。本轮**不能确定 400 的原因、发生次数、是否贯穿每一段，或究竟属于夹具、构建还是产品**。“两侧均 400、客户端编辑未落库、revision 只由种子推进”在这里保留为作者报告的现场描述，没有伪装成已独立查库或读到原始 HTTP。

固定源码已足以反驳“它与交互测量无关”这种绝对说法；与现场是否实际命中该分支分开看。对应原始源码摘录、原文件哈希和行号见 [source-excerpts.json](2026-10-28-canvas-connection-index/16d2e903/source-excerpts.json)。

| 源码事实 | 对测量解释的影响 | 本轮不能断言的现场结果 |
| --- | --- | --- |
| 控制器先 `setConnections`，必要时 `setNodes`；生命周期把编辑写入 store，再在 500 ms 后排后端同步 | 失败之前仍可能执行本地投影、规范化、日记和发送准备；这些成本多在落点计时之外，却可落在 FPS 窗口里 | 不知道各段发送了几次、落在哪一帧；不能量化污染幅度 |
| `sendCanvasDocumentCommit` 只有成功才 `applyAcceptedCanvasSave`，推进确认版本与确认日记 | 保存 400 路径缺少成功确认及其状态更新，不能代表正常成功保存过程的完整成本 | 不知道成功与失败哪个现场总成本更高，也不能统一把失败视作额外固定开销 |
| 普通、非可重试且非 revision 冲突的 API 400 会清 `inFlight`；未知/可重试错误可保留原提交身份 | 必须有响应和日记才能判断后续的重试/读取状态；不能从 HTTP 状态一项推断全部错误分支 | **没有证据说现场一直保留在途提交或一直冲突** |
| `reconcileRemoteCanvasUnlocked` 遇 `inFlight` 返回 `deferred`，暂停提交时返回 `held`；有本地未确认改动时还会三路合并 | 失败后的本地编辑与直接改库的远端 revision 可能改变应用、延后或冲突行为；“相同/旧 revision 直接忽略”也要求相应已确认基线 | 不知道本次远端标题是否真正应用到编辑器；单有长帧不能证明走完了应用 |

因此作以下判断：

- **可保留局部读数**：保存失败不会让已发生的 `dropTargetCalls/dropTargetMs` 汇总自动消失，落点回调也没有在内部等待保存。4000 档的巨大局部成本差仍是有用方向，不能仅因 400 把这类观察全部作废。
- **不能保留的强结论**：成功保存验收、完整生成/自动取回/绑定/保存验收，以及“400 不影响帧率、重建或远端应用结论”。如果保存失败改变了未确认文档、成功回执、新数组或后续合并，冷热成本和整窗 FPS 都可能变化；目前不能排除。
- **需要条件明确的补采样**：在 #95 查清并纠正夹具后，读到一次成功保存及相同版本的重新加载，再做原定完整过程和受控前后对照。若原日志证明某个旧局部段与保存完全无关、输入和状态也满足约定，可以直接保留该段；不要求因一个错误重跑全部产品研究。

### 6. 悬停、浮层和远端快照：哪些观察还成立

- **悬停/导航仍有长帧的现场记录可保留。** 汇总确实写出悬停 53.3/54.8 fps、导航 32.4/34.5 fps；候选没有任何落点调用。这支持“本候选没有提供这些路径已改善的证据”。投递窗口前置、实际视口及缓存状态未受控，不能写成两侧等效，也不能把 32–35 fps 当作纯应用导航成本。这里无需为连线结论重采整套悬停研究。
- **浮层计数差可以保留为基线单侧观察。** 100% 档两次均 1224 帧、13 张挂载卡；active/idle 的页面执行计数为 36/6，节点执行计数为 44/0，进度查询为 88/0。探针插在组件函数体，计的是**组件执行次数**，不是 React commit 次数或耗时。它支持活动任务与额外执行同时出现，不能独立证明唯一原因或未来生成更新不会掉帧；整窗平均 60.0 也不等于每帧稳定。
- **可见性轮询只剩源码与作者描述，原生请求序列未核实。** 源码的活动查询间隔确实是有任务 2 秒、无任务 10 秒；但最小化 60 秒时 0 次、兜底由 4 秒变 5 秒、恢复后的周期和后端每次 26–37 ms，依赖缺失的访问日志。本轮不认证这些现场数字，先找原件，找不到再只补这段。
- **远端 revision 样本证明的是两个存在长帧的记录段。** 第 3/4 段均 `gt100=2`，最大分别 159/143 ms。不能从一个窗口最大值把“每次应用耗时”定为 143–159 ms，更不能说整段只卡一帧。记录没有远端改库/读取/合并起止、实际应用读回或主线程栈；“成本在反序列化和对账、不在 React”只是待定位解释。它们也没有对应 after 样本，不能写成两侧均测。保留为定位线索，完整后台取回与成本归属仍待原计划补测。
