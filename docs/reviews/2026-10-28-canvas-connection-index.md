## 需要修正的发现

### P2：索引的严格矩形相交漏掉原来接受的吸附圆边缘

位置：候选 `web/src/lib/canvas/canvas-connection-target.ts:62`，以及已有 `canvas-spatial-index.ts` 中的 `intersects`。

旧判定是 `dx * dx + dy * dy <= radius * radius`，圆周也接受。新代码先用未扩大的节点矩形和指针周围矩形查询索引；已有空间索引故意只接受严格相交，矩形相切就丢弃节点。节点没有进入候选列表，后面的圆形判定无法补救。

最小复现：目标图片左上角 `(1000, 0)`、尺寸 `320 × 180`，从另一个图片的输出端拖线，100% 缩放、指针在 `(944, 90)`，恰好位于左输入端外侧 56 像素。结果如下，普通和批量拖线均复现：

| 返回或最终动作 | 基线 | 候选 |
| --- | --- | --- |
| `nodeId` | `target` | `null` |
| `isNearNode` | `true` | `false` |
| 松手后 | 连成线 | 打开创建菜单 |

后果来自真实 `finishConnection` 的分支：有目标则连接，只有 `isNearNode` 则取消，其余打开创建菜单。批量拖线也按这个标志决定是否创建节点。该位置在节点外，依靠 window 的松手处理；不能用“端口自己的 pointerup 会直接连接”消除这条回归。

证据：

- [differential.json](2026-10-28-canvas-connection-index/differential.json)：2740 次定向差分中有 15 个精确相切差异，其余取样未发现差异。覆盖普通/批量、正向/反向、多个缩放；反向批量不适用的组合返回空，没有冒称覆盖。
- [hook-browser.json](2026-10-28-canvas-connection-index/hook-browser.json)：36 条真实前后 `useCanvasConnectionController` 路径，用浏览器分发 `PointerEvent`，经过 rAF、状态更新和松手分支。100% 下距离 55、56、57 像素分别检查；56 像素时普通和批量均从“连接”变为“创建菜单”。
- 这是无头 Chromium 的 hook 复放，未渲染实际画布、媒体与世界层；AntD 消息和插件持久化被替身隔离。没有把它写成原生鼠标、完整客户端或 FPS 验收。

最小修正方向：让连线专用索引的粗筛选包含圆周可能命中的节点，再保留原有精确圆形判定。不要直接修改共享空间索引的严格相交规则，现有裁剪等调用有意依赖该规则。补精确左右边缘、缩放和跨网格位置的普通/批量回归，并验证 `isNearNode` 及最终菜单分支。

### P2：原报告不足以证明用户场景收益，且误判了可达输入

位置：作者 `docs/performance/2026-10-28-canvas-interaction.md` 的结论、复现与限制；`web/scripts/canvas-interaction-bench.ts:146`、`:183`。

以下修正会直接影响“保留还是撤回”的判断：

1. **末尾背板有现成入口。** `use-canvas-node-operations.ts:288` 的 `createStoryboardGroup` 和 `:339` 的 `createReferenceGroup`，对已有图片/视频设置 `parentId`，再把新 frame 追加到数组末尾。`project.tsx:3108`、`:3109` 已接到多选工具栏。无需先重排 `nodes`，`isNodeHiddenByCollapsedFrame` 便会逐子节点找到末尾背板。作者人工构造的“末尾批次根”不因此自动得到可达性证明，但不能把背板和批次根一起排除。
2. **作者只测了热查询。** `measure` 先预热，再反复使用同一 `nodes`；首次索引建立已经被排除。标题、进度、尺寸等更新换数组后的重建也没测。作者报告里的速度比只能用于这条热路径。
3. **差分不是 5000 节点覆盖。** `parity` 的规模固定为 `[100, 300, 500]`，不受 `--nodes 5000` 控制。5400 次是全部夹具、规模、缩放的总数；只调用普通 resolver，没有调用批量 resolver。随机平面取样不能代替精确圆周、滚动分镜与节点更新场景。
4. **测量顺序不是逐样本交替。** 每一场景先完成整个 `legacy: measure(...)`，再完成整个 `current: measure(...)`。同进程能减少一些差异，仍不能据此认定并发机器负载不影响比值。本次补测按样本交替前后顺序。
5. **原有浏览器测试没有经过新落点入口。** `canvas-connection-drag.browser.test.ts` 验证已有连线在节点拖动预览时的曲线更新，夹具调用 `applyCanvasNodeDragPreview`；它未导入这次的控制器或 resolver。它通过不能证明新拉线落点与松手保持一致。

因此搁置任务材料中沿用的“最坏根节点顺序不可达”判断：代码证明至少末尾背板可达。也不采纳作者报告中“300 节点三条路径都不是主因”的整体排除结论：本轮能够验证的只有局部逻辑，缺少完整桌面事件、页面更新和绘制证据。这些是证据解释修正，没有扩大产品规则或授权范围。

原作者脚本也已独立复放，见[author-replay.json](2026-10-28-canvas-connection-index/author-replay.json)：`--nodes 300 --entries 60 --repeats 60`，取得 5400 次差分、0 差异。这个结果与本文发现可以同时成立：它没有定向覆盖本文失败输入。原作者测量可复放，不代表原报告对覆盖范围和真实收益的所有解释成立。

## 行为与索引生命周期

已有 34 项专项测试全部通过，见[submitted-tests.txt](2026-10-28-canvas-connection-index/submitted-tests.txt)。包括作者新增的 15 项落点测试、13 项批量连接相关测试和 6 项空间索引测试。首次隔离提取曾缺少后端静态 JSON，补入固定版本依赖后才取得此通过结果，未修改产品或测试断言。

独立取样覆盖：文档顺序靠后的合法节点优先、上层不合法仍寻找下层、源自身的靠近标志、已有连线、背板/批次折叠与展开、脚本行/上下文和滚动位置、批量表参考列、正反向端口、多个缩放、移动后的新旧位置、重新排序和零尺寸节点。除精确相切外未发现差异。这是有限取样，不是所有输入等价证明，也未改变既有“文档顺序”选择为“视觉叠放顺序”。

缓存按 `CanvasNodeData[]` 身份存于模块级 `WeakMap`。当前核对的 `project.tsx:233` 的 setter、`use-canvas-node-editor.ts` 的改名/尺寸/展开、`use-canvas-generation.ts:243` 的任务回填，均通过新数组传入；没有发现这些入口把已索引数组中的坐标就地修改后继续复用旧键。数组换新后查询使用新数据，配置、连线、脚本滚动也在每次查询时读取。WeakMap 本身不要求显式释放旧数组，也没有另建一套持久业务状态；未做堆快照，因此不宣称已经排除所有内存问题。

**正确失效不等于失效便宜。** 仅变更非几何数据也会重建全部索引。本次以实际 `updateCanvasNode` 给 300 节点中的一个节点更新 `taskProgress`，数组换新后查询读取其余 299 节点的 `position` 共 1196 次；同数组的热查询为 0 次。实际生成回填的 `canvasGenerationTaskNodes` 也使用 `nodes.map` 返回新数组。这项重建由下一次查询惰性触发，**不是每次进度更新都立刻建立索引**；停止拖线期间的多次更新可以只在下次查询建一次。不能把它说成陈旧索引缺陷，也不能把热查询当作稳定只读附近节点的完整成本。

## 计入建立与更新后的性能

本次新增[独立测量](2026-10-28-canvas-connection-index/independent-bench.json)，直接调用固定候选和自动提取的旧回调。普通网格、批次根在前、背板在前，以及从真实创建分镜组回调产生的末尾背板，分别计时。每个样本交替前后执行顺序，保留中位数和 p95。

`first-query` 包含首次建索引及查询；`progress-update`、`title-update`、`geometry-update` 包含真实 `updateCanvasNode` 的局部修改及随后查询；`60-query-drag` 包含首次建立和总共 60 次查询；另测每 15 次查询换一份进度数组，共建立四份索引。批量补测还包括真实 `planBatchConnections` 与源资格检查，但不含 DOM、React 和绘制。这些数值是同机 Bun 的逻辑成本，**不是完整拖线墙钟时长或 FPS**。

以下为中位数，单位毫秒，每格“旧 → 新”。“分镜组 N”是给 N 个已有节点中的 N−1 张图片创建分镜组，实际数组再多一个末尾 frame；其创建方式来自产品回调。

| 场景 | 热查询 | 首次建立并查询 | 更新单节点进度并查询 |
| --- | --- | --- | --- |
| 普通 300 | 0.0128 → 0.0038 | 0.0130 → 0.0325 | 0.0165 → 0.0348 |
| 普通 1000 | 0.0511 → 0.0102 | 0.0498 → 0.1055 | 0.0593 → 0.1135 |
| 普通 5000 | 0.2121 → 0.0476 | 0.2035 → 0.5344 | 0.2506 → 0.5677 |
| 分镜组 300 | 0.3150 → 0.0064 | 0.3029 → 0.0400 | 0.3228 → 0.0421 |
| 分镜组 1000 | 3.3393 → 0.0194 | 3.2515 → 0.1263 | 3.4649 → 0.1660 |
| 分镜组 5000 | 92.6336 → 0.1029 | 91.5413 → 0.7509 | 97.9598 → 0.7835 |

普通 300 节点每次热查询约省 0.009 毫秒，首次或更新后一次查询反而多约 0.02 毫秒。这支持“函数更快”，不能单独支持“用户感觉不再卡”。连续 60 次、计入首次建立的查询总 CPU 时间为 `0.774 → 0.245` 毫秒；若期间每 15 次更新进度，则为 `0.780 → 0.341` 毫秒，收益仍很小。

真实分镜组改变了判断：1000 节点首次查询从 `3.251 → 0.126` 毫秒，更新进度并查询从 `3.465 → 0.166` 毫秒，60 次查询含三次中途进度更新的总 CPU 时间从 `203.177 → 1.732` 毫秒。5000 节点分组的旧查询约 90 毫秒量级，超出常见一帧预算；该输入经产品代码可构造，不能仅当作无法到达的人工最坏排列。不过本次没有在完整客户端创建并拖动这一规模。

批量拖线加上 20 个源的真实规划和资格检查后，普通 1000 节点约 `0.251 → 0.221` 毫秒，分镜组 1000 节点约 `3.120 → 0.222` 毫秒；普通画布的整段逻辑收益明显小于单看 resolver 的倍数。源节点多时剩余规划和 `find` 仍会占成本，本次没有新提批量算法重构。

标题、几何更新和其余场景共 128 组统计均在 JSON 中。不能用“索引永远只访问附近节点”描述首次建立或更新；也无需在这个候选里立刻增加第二种几何版本状态。已有共享空间索引得到复用，普通/批量规则通过回调共用，没有证据要求扩大结构重构。

测量环境和负载见[environment.json](2026-10-28-canvas-connection-index/environment.json)、[measurement-load.json](2026-10-28-canvas-connection-index/measurement-load.json)。1000/5000 分镜组的 60 次查询场景仅 12 组配对样本以控制成本，其 p95 不作可靠尾延迟结论。该规模通过产品入口的代码可达性不等于用户当前工程正有这么多节点。
