## 1. 结论

1. **吸附圆精确相切处会漏接并误开创建菜单**（复查 P2）。已按「只放宽连线粗筛、不动共享空间索引」做最小修复；锁住它的是边界差分（2880 组，旧索引 144 组位置不一致 → 修正版 0）与**真实控制器入口回归**（`web/test/canvas-connection-drop.browser.test.ts`：相切位置连成线、相切外 1 px 打开创建菜单、0.6×/2× 缩放同样如此）。这是第二轮唯一新增的产品行为修正，第三、四轮没有再动产品代码。
2. **索引改动的收益取决于画布形态**：普通画布热查询变快但幅度很小（300 节点每次省约 0.009 ms），首次建立和更新后重建**更贵**；真实分镜组画布（背板在数组末尾）收益明确（1000 节点首次查询 `3.251 → 0.126 ms`）。
3. 因此结论是**有条件保留**：不以「最坏输入不可达」撤回，也不以热查询倍数当作已解决。
4. **完整 Mac 客户端的帧率定量对比已在第五轮完成**（第 5.7 节）：连线手势 4 个规模档 × 3 次真实拖拽，悬停、平移缩放与 #96 三项各有覆盖。第 5.3 节的干跑数字仍只能当路径连通性证据。
5. **第五轮结果（一句话）**：连线落点解析的单次成本在 4000 节点上从 `45.5 / 50.2 ms` 降到 `0.54 ms`（301→2000 节点各档同向，差 2.6–93 倍），但**可见帧率差别只在 4000 节点档出现**（基线 48–50 fps → 候选 59.4 fps）；301/1000/2000 三档两侧都是 59–60 fps，看不到可见改善。同一块 4000 节点画布上，悬停（53–55 fps）、画布导航（32–35 fps）与一次外部画布快照变更（卡 143–159 ms 一帧）两侧一样，**不构成「整体卡顿已解决」**。完整读数与不可归因说明在第 5.7.4–5.7.7 节。

## 2. 吸附圆精确相切漏判：复现、最小修复、回归

### 复现

目标图片左上角 `(1000, 0)`、尺寸 `320 × 180`，从另一张图片的输出端拖线，100% 缩放，指针在 `(944, 90)`（左输入端外侧 56 px，正好相切）：

| 返回或最终动作 | 基线 | 候选（修复前） |
| --- | --- | --- |
| `nodeId` | `target` | `null` |
| `isNearNode` | `true` | `false` |
| 松手后 | 连成线 | 打开创建菜单 |

复现脚本在 `web/.local/canvas-interaction/repro-tangent.ts`（临时目录，收尾已删）；结论与 #101 的 `hook-browser.json`（36 条真实 hook 路径）一致。

### 根因

查询矩形用吸附圆的外接矩形，而共享空间索引的矩形相交是**严格比较**（`left.right > right.left && left.left < right.right`）。端口锚点落在节点边界上（`position.x` / `position.x + width`），左右相切时节点边界与查询矩形**只共边**，整条被丢弃；后面的精确圆判定（`dx² + dy² <= r²`，闭区间）根本没机会跑。

### 最小修复

`web/src/lib/canvas/canvas-connection-target.ts`：

- 新增 `queryBounds(world, handleRadius)`：查询矩形按 `Math.max(1e-6, |world.x| * 1e-12, |world.y| * 1e-12)` 外扩，让闭区间的边界命中也进入候选；真正命中仍由原来那次精确圆判定决定。
- `snapBounds` 改为 min/max 归一（覆盖负向/零尺寸卡片），保证节点自身边界一定是有效矩形。
- **没有改共享的 `canvas-spatial-index.ts`**：它的严格相交被 `canvas-selection.ts`、`canvas-frame.ts`、`use-canvas-render-model.ts` 的裁剪等调用有意依赖。

### 回归证据

- `web/test/canvas-connection-target.test.ts`（19 条，全过）：精确相切命中、相切内外 0.5 px 分界、相切位置上的非候选节点仍 `isNearNode=true`、容差不把圆外节点带进来。它**只覆盖 resolver 几何**：文件里的「最终动作」是测试内重写的三元表达式，不能当真实松手分支的证据（第 0 节末表）。

### 3.3 怎么读这张表

- **热查询**变快，普通画布幅度很小（300 节点每次约 0.009 ms），真实分组画布幅度大。
- **首次建立**和**更新后重建**更贵：仅变更非几何数据（例如 `taskProgress`）也会换数组、下次查询时重建全量索引。
- 重建是**惰性**的：不是每次进度更新都立刻建索引，停止拖线期间的多次更新可以只在下次查询建一次。所以不能把它说成「陈旧索引缺陷」，也不能把热查询当作完整成本。
- 普通画布上「函数更快」不能单独支持「用户感觉不再卡」；真实分镜组才改变了判断。

#### 5.7.3 采样协议与可比性条件

`round.sh <before|after> [seed 额外参数]`：杀 app → 归档该侧 WKWebView 存储 → 删 `runtime.json` → 同一份种子写回同一块画布 → 启动 → 固定窗口 `x=-1440,y=0,w=1440,h=960`（Yomado 虚拟屏）→ 关闭 Agent 面板 → 探针报端口坐标 → 把指针放进窗口 → `perf-rec-start` → 3 次 foreground 拖拽 → `perf-rec-stop` → 读 ndjson。

- **同一块虚拟屏一次只跑一侧**：两侧同跑时前台像素拖拽会落到前台那个窗口，另一侧记 `落点调用=0`。
- 可比性证据是**两侧探针报出的 `卡片中心` 集合相同**（`{350,870}×{90,450,810}`），不是 `in`/`out` 相同：`perf-ports` 的 `nodes` 取「完全在视口内且四周留 60px」的卡、`first = nodes[0]`（DOM 顺序），1000/2000 节点画布上 DOM 顺序在两次读取间真的变过（`perf-child-32 ↔ 33`、`45 ↔ 46`）。
- 拖拽路径固定为「左侧卡的输出连接点 → 右侧卡的卡片中心」，两侧用同一组截图像素 `(569,457) → (825,457)`、`duration_ms=1000`、`steps=20`。
- 画布种子 `seed-canvas.py --group-all-children`：全部图片节点带 `parentId` 指向末尾展开背板，与 `use-canvas-node-operations.ts:312` 的 `collapsed: false` 一致；间距 `520×360`，大于渲染后的 420×234 卡片，保证连接点完全落在空隙里（早先 360×240 会让相邻卡重叠约 60px，被压住的连接点按不到，`落点调用=0`）。
- **种子必须让 revision 前进**：客户端把 revision 相同或更旧的远端快照当本机回执忽略（`local-workspace-repository.ts` 的 `reconcileRemoteCanvasUnlocked`），固定写 1 时界面一直显示缓存里的旧画布。
- 清空 WebKit 存储会重置新手引导，每轮多一步「稍 后」，首屏状态与不清缓存时不同——这是人为引入的每轮固定步骤。
- 接收端 `perf-sink.py` 本轮改成 `protocol_version = "HTTP/1.1"` + 显式 `Content-Length`：此前默认 HTTP/1.0 关连接，出现过一次 `perf-rec-start` 点击产生 2–3 条 `start` 记录、后几条正好在拖拽中途把计数器清零。改后本轮全部 20 次录制都只有一条 `start`。

  两次都得到 `max 143–159 ms`、`>100ms = 2`，**可复现**：应用一份 2.37 MB 的 4000 节点画布快照，主线程会卡约 143–159 ms 一帧。页面/节点渲染次数几乎不变（`页面渲染 6→8`、`节点渲染=0`），代价在反序列化与对账，不在 React 渲染。
- 4 秒兜底轮询**本身**在画布没变时很便宜：客户端先比 revision，`reconcileRemoteCanvasUnlocked` 在 `remote.revision <= confirmedRevision` 时返回 `stale`，不 `setNodes`（上表「空闲」行 `页面渲染=6 / 20 s`）。后端侧每次 `GET /canvas-projects/perf300` 仍要序列化 2.37 MB，实测 26–37 ms。
- **没有覆盖**：真实上游取回（需要常驻假上游 + 一条绑到它的模型渠道 + 带真实 `provider_request_id` 的任务），本轮未做；因此「生成中 + 后台自动取回叠加」只在客户端一半上有数据，后端一半仍是 #96 的缺口。

#### 5.7.7 现场条件与不可归因说明

- 采样窗口 14:16–14:58，`uptime` 1 分钟负载 3.9–9.1（10 核）。逐轮：301 档 before 5.7 / after 6.6；1000 档 before 6.0 / after 5.3；2000 档 before 6.0 / after 5.3；4000 档 before r1 **9.1** / before r2 5.4 / after 4.9；悬停导航档 3.9–6.0。
- 同期 top CPU：BetterDisplay 约 52%、WindowServer 约 49%、cua-driver 约 44%、Todos Helper 约 38%；`mds_stores` 仍在索引本轮搬到外置卷的工作树。**这不是一台安静机器。**
- 前后交替能减少漂移，**不能保证抵消** mds、其他程序与内存压力带来的干扰；4000 档基线两次运行的 fps 是 50.4 与 48.1、`>50ms` 帧 13 与 42，同一侧内部就有这个幅度。
- 因此本报告的读法分两层：**「每次落点调用耗时」**（同步 CPU 计时，跨规模单调、量级差 2.6–93 倍、可复现）可以归因给候选；**「fps / 尾延迟」**只在 4000 节点档给出方向性结论（基线 48–50 fps、候选 59 fps，两次基线运行一致低于候选），其余档位写「本轮无法归因」。
- 一条未定位的现场问题：两侧隔离客户端的 `POST /api/ops/canvas.document.commit` 都返回 **400**，画布头部因此一直显示「画布保存状态：保存失败」，客户端自身的编辑从未落盘（隔离库里 revision 始终由种子推进）。它与本次交互测量无关（测的是交互，不是保存），但**排除了「客户端自己保存成功」这条解释**，400 的具体原因未查清。

## 8. 保留还是撤回

**有条件保留，第五轮把条件收紧了一步。** 理由与条件：

- 保留的依据（第五轮实测，第 5.7.4 节）：真实展开分组画布上，单次落点成本随规模线性拉开的差距被实测出来——301 节点 `0.62 → 0.24 ms`、1000 节点 `3.58 → 0.19/0.20 ms`、2000 节点 `13.55 → 0.29 ms`、4000 节点 `45.5/50.2 → 0.54 ms`。相切漏判已修，有边界差分（旧索引 144 组 → 0）与真实控制器入口回归（`canvas-connection-drop.browser.test.ts`）锁住；索引按数组身份缓存，没有新增需要同步的状态。
- **「首次建立 / 更新后重建带来可见停顿」这个撤回条件没有被触发**：候选侧 4000 节点手势里索引重建只花 **2 ms**（2000 节点 1 ms），整个手势 63 次落点调用合计 34 ms。
- **「目标画布无可见改善」这一半部分成立，取决于规模**：301 / 1000 / 2000 三档两侧都是 59–60 fps、`>50ms ≤ 1`，**看不到可见改善**；4000 节点档才有可见差别（基线 48–50 fps、`>33ms` 占 11% 的帧、`>50ms` 13–42；候选 59.4 fps、`>33ms` 占 2%、`>50ms = 0`）。所以保留与否取决于产品要不要为大画布（约 4000 节点、展开分组）背书，不是「任何画布都更快」。
- **不能写成「整体卡顿已解决」。** 同一块 4000 节点画布上，悬停 53–55 fps、画布导航 32–35 fps（`p99` 300–363 ms），两侧一样；一次远端画布快照变更会让主线程卡 143–159 ms 一帧（第 5.7.5、5.7.6 节）。这些路径与本候选无关，也没有被它修好。候选解决的只是**连线落点解析**这一项成本。
- 若最终选择撤回：**不需要额外保留相切修复**。相切漏判是首轮索引引入的回归，原产品基线（`6a155448`）没有这个缺陷：原控制器用 `<=` 的闭区间圆判定，在精确 56 px 处本来就连成线，基线里也没有 `canvas-connection-target.ts` 这个文件。一旦撤回索引、恢复原控制器扫描，圆周命中与命中顺序随原实现一起恢复；`queryBounds` 的外扩只是让新索引恢复原结果的配套修正，不是独立的产品收益。若后续选择「保留函数提取、只移除索引」，那是另一种具体改动，仍以原基线结果为准，不能为了留下「正确性修复」而强留索引模块。

第四轮只补测量材料，不改变上面的判断；第五轮把正式采样跑完了（第 5.7 节），它改变的是「这条候选到底值多少」：连线落点解析的成本差已被真实原生客户端量化到 84–93 倍（4000 节点），但可见帧率差别只在 4000 节点档出现，且悬停、画布导航、外部画布变更这三条同机路径仍然卡。**保留与否的剩余问题不是「候选有没有用」，而是「产品要不要为约 4000 节点的大画布背书」——这一条需要产品判断，不在本报告的测量范围内。**

后续修改需对新固定提交复查，本报告结论不自动外推到修正版。
