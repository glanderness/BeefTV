## 4. 逐项实施建议与验收

### 4.1 Seedance：先确认上游接收素材，再确认作品能保存

**目标仅是会议指定的 Fast / Mini。** 2.0 标准版和 2.5 继续沿会议指定渠道，不顺便迁。会议说法不足以确定具体 API 产品、地域、模型 ID 和权益适用账户；Lucas 提供实际商务订单与权益，Sunny 对照 BeefAPI 现有模型映射核实。不能按中文“官方”推断是方舟、BytePlus 还是某个转售接口，也不把优惠金额写进产品代码。

先做以下准备，11 月 1 日是目标窗口，不是跳过验收的理由：

1. 读取原渠道和候选渠道的配置快照，列出对外模型名、实际模型版本、分组、路由、价格和权益生效时间。凭据只走现有安全配置，不进入报告。
2. 输入方向：用 BeefTV 实际素材提交路径，检查官方服务能否读取上传/签名后的图片、首尾帧及已支持的参考视频、音频；记录 URL 有效期、过期行为、重定向和文件类型。**本机能 GET 不足以证明供应商可下载。** 核对 `seedance_preupload.go`、`seedance_upload_transport.go`，缺陷在哪层就在哪层修。
3. 输出方向：同一上游任务号查询成功 → 输出 URL → 本地素材入库 → 画布可播放 → 重启后仍在。下载超时、过期和暂时断网只取回已有结果，不创建第二次生成。
4. 经批准的试验组验证后再切新任务。已有任务仍用原渠道身份查询；回退只改变后续新任务的选路，不搬运在途任务，不向备用渠道自动重放未知提交。

**验收证据：** 两个模型分别保存对应模式的请求摘要、任务号关联、脱敏错误分类、产物哈希/时长和重启回读；把“输入下载失败”与“输出保存失败”分别注入本地测试；真实供应商部分记录实际费用及重复提交次数。任一必需模式不可用、来源身份无法保留或下载失败会变成新提交，则不切该模型。

与 #25 的关系：#25 只处理图片恢复，不是视频全链验收的替代。渠道配置、输入可达性检查和既有视频协议验证可以先做；若需要修改共用 `app/service.go`、`task_delivery.go`、`generation/http.go`，在 #25 合入后同一负责人继续。#32 的视频扣费查询设计还未实施，不得宣称迁移自动获得它。

### 4.2 DeepSeek：改默认选择，不再重复接渠道

已核事实：`web/src/lib/assistant-model.ts` 的托管名单含 `deepseek-v4.1-flash`；`backend/internal/beefapi/catalog.go:12` 的默认仍是 `gpt-6-astra`。目录刷新经 `SaveCatalogWithAssistantDefault` 保存初始化，React 的 `assistantModel` 空值表示跟随文本默认。这是三个不同职责。

建议把托管助手的新初始化默认改为目录实际存在的 `deepseek-v4.1-flash`，保留既有别名、协议和可用性校验。**不新增火山专用开关，不在前端写渠道 ID，不为了这个改 BYOK 文本默认。** 不覆盖已保存的用户选择；旧用户可从已有模型选择器切换。不能仅看到旧值是 Astra 就认定它从未被用户选择。

实现时检查重新授权也可能触发初始化的路径，明确新用户、同账号刷新、重连、换账号和用户主动改选的行为；优先沿用现有配置来源和初始化标记，不新增第二套“推荐模型状态”。若负责人要强制迁移存量默认，这是额外产品选择，另决策。

**验收证据：** 新连接实际目录有 Flash 时默认选中；目录缺失/读取失败时不虚构模型；已有选择经刷新和重启保留。只读核对 BeefAPI 路由后，在批准的文本试验额度内，从真实助手发普通对话及只读画布工具调用，核对实际模型和响应；禁止用生成视频证明文本模型可用。火山故障后的备用规则沿用已有配置，本任务不改线上优先级。

### 4.3 流式：沿已有链路找停顿点

检查顺序：供应商首个可见文本 → Durable `message_update` → `durable-stream-text.mjs` → 宿主 NDJSON → `handler/agent_proxy.go` 写行并 Flush → `services/api/agent-assistant.ts` → `use-canvas-assistant.ts` → 回复组件。推理阶段没有正文与正文被缓冲是两种情况，不能用逐字动画掩盖真实等待。

已见一个可检验假设：根 `nginx.conf` 的流式特殊路由包含旧 Agent SSE 和系统模型路径，未包含 `/api/assistant/chat`；Go 虽 Flush，部署代理仍可能缓冲。**这是 Compose/Web 路径的疑点，不是 Mac 桌面故障的已证实根因。** 先用同一个慢速假模型对照直连与经过代理的响应时间，再决定是否仅补该路径；不能给全部 `/api/` 关闭缓冲或套长超时。

PR #265 正修改 `durable-session-owner.mjs`、回复回退和方案卡片，须先处理 #36 评审，再在同一结果上修改。保留官方 Durable 单一执行循环；停止、断线后查看历史、最终回执仍由原实现负责。不要把 `/tasks/:id/text-events` 的 SSE 游标规则移植到助手 NDJSON。

**验收证据：** 慢速替身分三个时间点发正文，界面在终态前显示多个片段；快照替换、工具前后正文、无正文提案、停止、断线恢复均不重复字、不丢字、不重复工具副作用。复用 `durable-stream-events.test.mjs`、`canvas-agent-assistant-stream.test.ts` 及助手浏览器用例；原生桌面和代理部署分别留记录。真实模型首字耗时作为观察值报告，不承诺固定秒数。

### 4.4 插件：先有第三方能照着做成的例子

第一阶段不是“插件中心能打开”，而是**开发者不用修改 BeefTV 源码，就能交付一个包，另一台干净环境安装后能完成工作**。

**A：声明式服务/工作流插件，1–3 天。** 复用 `.beeftv-plugin`、现有 `beeftv.plugin/v2`、后端 registry 和统一生成/素材流程。以已有 `autodl-comfyui` 或 `runninghub-workflow` 为路径参考，用本地假服务制作可复现样例，完成打包、安装、发现、选择、执行、查询、保存、停用、重启。它是可交付第一步，不等于任意 UI 扩展已完成。已有 RunningHub 名称与 manifest 存在也不证明所有用户实例兼容。

**B：一个外部界面插件，3–5 天起。** 选不收费、不读密钥的“自定义文字卡/素材标签”作为最小样例，先查声明式节点 renderer 能否满足；能满足就不新增脚本执行器。必须执行第三方代码时，在现有包 `entry/runtime.web` 合同下实现一个隔离入口，只给样例实际需要的读画布、改自身字段和本地插件数据能力。宿主负责身份、画布版本、写入和资源访问，插件不能直接读 store/数据库或自行提交生成。运行能力不足时报告具体缺口，重新估算；不要顺手开所有编辑器插槽、外部进程和网络权限。

复用来源：后端 `internal/plugins` 是安装和可用性的权威；`web/src/lib/plugins/plugin-registry.ts` 管激活后的贡献；`use-plugin-store.ts` 保留既有用户配置职责，不能另建同名包目录或另一套安装状态。当前内置应用的静态 `registerPlugin` 不等于上传包已执行。`plugin-system.mdx` 的 v1 示例和“替换内核尚未落地”段落与现状不符，实施时修文档，不照旧文档恢复旧宿主。

**#33 是包升级、撤下和回退的前置条件。** 在其完成前可以准备样例、测试和接口清单；不另改 `plugins/bootstrap.go`、registry 持久化或旧配置清理。执行中的任务保留原协议引用，停用/卸载不删画布内容、不把旧任务改走新供应商。第一阶段通过现有上传入口和版本化归档分发；公开投稿、审核、搜索、分成以后独立评估，不能套用 Skill 投稿已完成的结论。

**验收证据：** 从独立目录打包，干净安装可用；升级后配置不丢，回退恢复旧包；停用后不接受新调用且既有数据保留；缺包、越权、坏包和任务未结束时给出明确结果；用户界面与后端 registry 一致；实际发行包也包含需要的产物。A、B 分别留录像/运行记录，只有两者都完成才称“已验证服务和界面两类扩展”。

### 4.5 Mac：先区分看不见与数据真丢了

当前已有 LOD 缩略图、视口虚拟化和活动媒体选择，集中在 `canvas-lod*.ts`、`canvas-performance-mode.ts`、`canvas-viewport-render-sync.ts`、`pages/canvas/project.tsx` 及 `canvas-project-world-layers.tsx`。不能从会议“Mac 更卡”直接推断是 Wails、GPU、React 或数据库的问题，也不要再建一套缩略图缓存。

先冻结相同项目副本：少量节点、约 100 个混合节点、约 300 个节点三个档位；比较真实 Mac 桌面 WebView、同机浏览器和可用的 Windows 桌面。分别记录纯图片、单视频播放中平移缩放、跨视口移入移出、频繁选择、前后台切换。收集帧耗时、长任务、解码/内存和渲染次数，找到一条稳定复现后只改对应责任层。

显示可见集合只影响渲染，不能作为保存节点列表。每次优化都检查节点 ID、连线、资源引用、当前任务关联和保存版本；“吞节点”必须区分虚拟化暂时没画出、旧回执覆盖关联、持久数据真的缺失。后两项不能用延长动画或重绘掩盖。

**建议验收门槛（工程判断）：** 同机同素材同手势跑三轮，主卡顿场景的 P95 帧耗时较基线下降至少 30%，其余固定场景不恶化超过 10%；未达时先报告测量而不是宣称流畅。节点/连线/资源引用在保存重开后完整，交互回放中零丢失、零重复；明暗主题、弹窗、选择编辑、视频首帧和缩放切换无可见闪烁。使用现有 `canvas-lod-interaction.browser.test.ts`、`canvas-media-performance.test.ts` 和首帧回归，但不能以 Chromium 测试代替 Mac WebView 验收。

若动到任务状态/保存代码，等 #25 与 PR #265 相关修正后继续；若只是媒体可见性和绘制，可独立推进。回退该局部渲染改动即可，不迁移用户数据。

### 4.6 GitHub Issue：独立采集、写同一张需求表

建议主力复用 #12 的飞书目标表和“重复反馈并入原行、追加带日期进度”规则，新增 GitHub 来源采集，保持原企微任务的来源与时间范围。实现放团队自动化的现有位置；**不向 BeefTV 加 Webhook 服务、定时 Worker 或登录功能**。

需求表是跟进结论的来源，GitHub 是 Issue 原始内容的来源。标题/正文变化可同步来源摘要，人工负责人、优先级、进度说明不被覆盖；Issue close/reopen 作为来源事件记录，不能自动宣布需求已解决。避免与 #12 同时更新同一行时覆盖对方内容，写前读最新进度并合并。

目标表暂无独立来源键字段时，先用现有进度/来源文本中的规范 URL 做可核对标记；重复量足以证明需要字段时再申请改表结构，不偷偷增加字段。PR API 与 Issue API 结果要区别，不能把每个 PR 当新需求。

**验收证据：** 首次全量、第二次无变化、修改/关闭/重开、跨页、网络中断、写响应丢失及与企微反馈重复七类用例；同源唯一记录、人工字段保留、失败可重跑。先 dry-run，再经授权在测试表或批准行范围验证，最后启用周期任务。首版不自动改代码、不关闭 Issue、不发 GitHub 评论；是否发群沿此次同步任务获得的授权，不借用 #12 的发送授权。

### 4.9 实时语音：先算完整会话成本
