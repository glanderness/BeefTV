## 五、去重规则（三层，按优先级）

**L1 机器标记（权威）**：同步前读全表 `报错日志` + `进度说明`，用正则 `github\.com/glanderness/BeefTV/issues/(\d+)` 或 `GitHub Issue #(\d+)` 找标记；命中即并入该行，不新建。前提是**每次写入都必须留标记**——这是本方案能自洽的唯一硬约束。

**L2 人工等价表（覆盖存量）**：标记是这一轮才开始写的，表里已有的同主题行不会被 L1 命中，因此需要一份等价表（附录 A，本文件维护）。同步时先查等价表，再决定并入还是新建。

**L3 语义近似（只提示，不自动动手）**：把 issue 标题/正文关键词与全表 `需求内容` 做近似匹配，输出「疑似重复，请人工确认」清单。**不自动并入、也不自动新建**——误并会丢掉 issue 特有信息，误建会产生重复行。

判定原则（第七节 Q1 的答案）：**同一「诉求」并入；同一「错误信号但根因候选不同」新建并交叉引用**。例：`reczz28RZUXaynMg` 与 #118 都出现「结果尚未确认」字样，但前者是 400/超时被误判锁定、后者是批量单图任务丢结果，根因候选不同，因此按独立行处理并在进度说明里互相引用。

## 七、两个待确认问题的建议

### Q1 表里已有的需求和 issue 重复时怎么认？

三层规则（第五节）。补充两条操作细节：

1. **认行用 record_id，不用行号、也不用 issue 号**。表内行序会随排序/新增变化，且存在同名巧合（issue #112 vs 表内 `reczz28RZUfapWWV`）。
2. **并入时不要把 issue 的特有信息丢掉**：新信息（版本、诊断、维护者回复、复现步骤）追加进 `报错日志` 的编号列表，结论追加进 `进度说明`；只有确认是「同一诉求」时才并入，否则新建并交叉引用。

### Q2 issue 关闭后表里的状态要不要跟着改？

建议**不自动跟改**，改为在 `进度说明` 追加一行事实：

- 表里 `目前状况` 只有「已解决 / 正在处理」两个选项，且 `已解决` 的实际口径是「已核对并已发布」。GitHub 的 close 可能是 duplicate、not planned、被新版本取代或报告人自行关闭，语义不等价。
- 证据：5 条 closed issue 里 #68/#109/#113/#201 在表内**没有任何对应行**，#65 只与 `reczz28RaeeLQyMx`/`reczz28PgeY92CBH`（白膜/3D 预演）主题相近——历史上就没有「关闭回写」的约定。
- 反向例子更直接：#152 报告人 10-20 说「ok，关闭吧」、功能也已放开，但 issue 至今 open。说明 GitHub 状态与现场状态本就不同步，谁跟谁都不该自动跟随。
- 建议写入格式：`YYYY-MM-DD：GitHub Issue #N 已于 <日期> 关闭（原因 <stateReason>）；是否已随版本发布待核对。` 状态翻转仍按「已核对并已发布」由人工决定。
- 若确实需要表达「不做 / 已关闭」，需要给 `目前状况` 增加选项（写操作，需用户确认）；本轮不做。
