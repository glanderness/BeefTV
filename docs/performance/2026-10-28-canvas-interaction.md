## 1. 结论

1. **吸附圆精确相切处会漏接并误开创建菜单**（复查 P2）。已按「只放宽连线粗筛、不动共享空间索引」做最小修复；锁住它的是边界差分（2880 组，旧索引 144 组位置不一致 → 修正版 0）与**真实控制器入口回归**（`web/test/canvas-connection-drop.browser.test.ts`：相切位置连成线、相切外 1 px 打开创建菜单、0.6×/2× 缩放同样如此）。这是第二轮唯一新增的产品行为修正，第三、四轮没有再动产品代码。
2. **索引改动的收益取决于画布形态**：普通画布热查询变快但幅度很小（300 节点每次省约 0.009 ms），首次建立和更新后重建**更贵**；真实分镜组画布（背板在数组末尾）收益明确（1000 节点首次查询 `3.251 → 0.126 ms`）。
3. 因此结论是**有条件保留**：不以「最坏输入不可达」撤回，也不以热查询倍数当作已解决。
4. **完整 Mac 客户端的帧率定量对比本轮没做**。第三轮只把隔离客户端、真实鼠标路径、结果回传通道和夹具准备好，并跑了一次**干跑**（数据在第 5 节，明确标注了混杂因素，不作为 FPS 结论）。第三轮修掉了这批材料里会让正式采样失效的几处工具缺陷（第 0 节末表、第 5.5 节），因此第 5.3 节的干跑数字只能当路径连通性证据，不能当帧率证据。
5. **正式采样的准备缺口已补齐（第四轮）**：两个固定源码各自有一份能实际应用的同口径插桩补丁（第 5.6 节），共享探针模块逐字节相同，两侧都通过 `tsc --noEmit`，交叉归属互斥。**#88 已通知重负载全部结束、无遗留后台作业**，正式 FPS 采样的等待已解除；但本轮只交付并验证材料，**没有构建、没有启动客户端、没有跑原生测量**，正式采样与最后核验仍待执行（第 5.4 节）。

## 2. 吸附圆精确相切漏判：复现、最小修复、回归

### 复现

目标图片左上角 `(1000, 0)`、尺寸 `320 × 180`，从另一张图片的输出端拖线，100% 缩放，指针在 `(944, 90)`（左输入端外侧 56 px，正好相切）：

| 返回或最终动作 | 基线 | 候选（修复前） |
| --- | --- | --- |
| `nodeId` | `target` | `null` |
| `isNearNode` | `true` | `false` |
| 松手后 | 连成线 | 打开创建菜单 |

复现脚本在 `web/.local/canvas-interaction/repro-tangent.ts`（临时目录，收尾已删）；结论与 #101 的 `hook-browser.json`（36 条真实 hook 路径）一致。

### 根因

查询矩形用吸附圆的外接矩形，而共享空间索引的矩形相交是**严格比较**（`left.right > right.left && left.left < right.right`）。端口锚点落在节点边界上（`position.x` / `position.x + width`），左右相切时节点边界与查询矩形**只共边**，整条被丢弃；后面的精确圆判定（`dx² + dy² <= r²`，闭区间）根本没机会跑。

### 最小修复

`web/src/lib/canvas/canvas-connection-target.ts`：

- 新增 `queryBounds(world, handleRadius)`：查询矩形按 `Math.max(1e-6, |world.x| * 1e-12, |world.y| * 1e-12)` 外扩，让闭区间的边界命中也进入候选；真正命中仍由原来那次精确圆判定决定。
- `snapBounds` 改为 min/max 归一（覆盖负向/零尺寸卡片），保证节点自身边界一定是有效矩形。
- **没有改共享的 `canvas-spatial-index.ts`**：它的严格相交被 `canvas-selection.ts`、`canvas-frame.ts`、`use-canvas-render-model.ts` 的裁剪等调用有意依赖。

### 3.3 怎么读这张表

- **热查询**变快，普通画布幅度很小（300 节点每次约 0.009 ms），真实分组画布幅度大。
- **首次建立**和**更新后重建**更贵：仅变更非几何数据（例如 `taskProgress`）也会换数组、下次查询时重建全量索引。
- 重建是**惰性**的：不是每次进度更新都立刻建索引，停止拖线期间的多次更新可以只在下次查询建一次。所以不能把它说成「陈旧索引缺陷」，也不能把热查询当作完整成本。
- 普通画布上「函数更快」不能单独支持「用户感觉不再卡」；真实分镜组才改变了判断。

### 5.2 排障：本轮主要耗时（重要）

1. **数据目录不能放在外置卷**。重建后 ad-hoc 重签的客户端写 `/Volumes/ExternalWork/...` 被 macOS 权限拦住（TCC 按签名授权），表现是：窗口起得来、前端渲染出启动页，但**后端起不来、不写 `runtime.json`、不监听端口**。把数据目录换到内置盘（`/tmp`）后立刻正常。这是本轮排障花掉最多时间的一条。
2. **后台投递的拖拽在这个 WKWebView 里到不了连线端口**：`delivery_mode` 默认（不前置窗口）时拖拽事件被吞，`落点调用=0`；必须 `delivery_mode: "foreground"`（前置窗口 + 真实指针）才走到连线控制器。
3. 坐标换算：窗口 1440×960 pt，WebView 视口 1440×928 CSS、`dpr=2`；截图 1366 px 宽 → `pt = px × 1440/1366`，`CSS = pt − (0, 32)`。
4. 启动排障：客户端需要 `Contents/Resources/plugin-packages`（否则报「未找到官方插件目录」）。

2. 应用该侧的补丁：`git apply --unsafe-paths --directory=<检出目录> <该侧补丁>`，**`cwd` 用仓库根**（用仓库子目录当 `cwd` 会静默空跑，见第 5.6.2 节）。
3. 记录标识：`git -C <检出目录> rev-parse HEAD`、`git -C <检出目录> status --short`、该侧补丁的 `shasum -a 256`、完整构建命令。
4. 构建并隔离：按仓库现有方式出包，再 `prepare-native-app.sh <源 app> <目标 app> com.wails.beeftv.perfcanvas-before <版本串>`（after 用 `-after`）。
5. 起接收端：`python3 perf-sink.py --port 8799 --out <该侧的 ndjson>`，两侧各一个文件。
6. 每轮开始前用 `seed-canvas.py` 恢复同一块初始画布，核对节点数、连线数、视口与指定的源/目标。

本轮**没有执行第 3–6 步**：没有构建、没有启动客户端、没有跑原生测量。

## 7. 未测 / 限制

- **完整客户端帧率定量对比未做**：#88 的等待已解除，但正式采样本身仍待执行（第 5.4 节）；第 5.3 节的数据有混杂因素。
- 索引**内存**没做堆快照，不宣称已排除所有内存问题。
- 只测到 `p95` 尾延迟的 1000/5000 分镜组 60 次查询场景只有 12 组配对样本（#101 为控成本），不作可靠尾延迟结论。
- 连线拖动过程中每帧的 `document.elementFromPoint` / `closest()` / `getBoundingClientRect()`（参考图替换提示）没测；它们会强制布局，可能是同一帧里比落点判定更贵的一项。注意两侧的 `落点总耗时` 现在都**含一次** `screenToCanvas` 里的 `getBoundingClientRect()`：这是为了让两侧范围一致而有意放进去的，要看纯函数成本请用第 3 节的逻辑测量，不要直接读这一栏。
- 差分是**有限取样**，不是所有输入等价证明；也没有把既有的「文档顺序」选择改成「视觉叠放顺序」。第三轮的边界取样只覆盖两种画布形态（`mixed` 与展开的末尾背板分组）、每档 20 个目标节点，没有覆盖滚动分镜、批量表参考列的精确圆周、节点更新等全部组合；旧索引在同一批取样上的 144 组差异也不能与复查在原（空覆盖）取样上复放的 62 相互换算。
- 第三、四轮只修测量材料与报告，**没有重跑原生干跑**：第 5.3 节的干跑数字仍带探针缺陷与混杂因素，正式采样必须用修好的探针重做。第 5.6 节的复放只覆盖源码/补丁归属、完整应用、`tsc --noEmit` 与隔离 JS 探针，**不含任何原生运行**；它证明的是「材料能应用且口径一致」，不是「两侧都跑出了帧率」。
- 两侧的 `落点总耗时` 是**含坐标换算的控制器回调总耗时**，不是纯落点判定函数成本；两侧可比，但不能与第 3 节的纯函数数字混着读。
- 平移缩放的剩余卡顿不在本任务写入范围：既有证据在 `docs/reports/2026-10-27-mac-canvas-perf.md`（#40）与 `docs/reports/2026-10-27-mac-canvas-perf-fix.md`（#50）。截图里的「每次 patch 都做两遍全文档 JSON 规范化」「生成期间三层保存叠加」指向 `stores/canvas/use-canvas-store.ts` 与保存链路，属保存研究范围，本轮只留线索。

## 8. 保留还是撤回

**有条件保留。** 理由与条件：

- 保留的依据：真实可达的分镜组画布上，计入首次建立与更新后重建仍有明确逻辑收益（1000 节点 `3.251 → 0.126 ms`）；相切漏判已修，且有边界差分（旧索引 144 组 → 0）与真实控制器入口回归（`canvas-connection-drop.browser.test.ts`）锁住；索引按数组身份缓存，没有新增需要同步的状态。
- 条件：正式原生采样若显示目标画布没有可见改善、且首次建立/更新后重建带来可见停顿，则应**撤回产品索引改动、只保留研究证据**。也不需要等到「额外出现可见停顿」才考虑撤回：若目标场景既无可见收益、也无独立的必要正确性收益，就不足以为索引复杂度背书。
- **撤回后不需要额外保留相切修复。** 相切漏判是首轮索引引入的回归，原产品基线（`6a155448`）没有这个缺陷：原控制器用 `<=` 的闭区间圆判定，在精确 56 px 处本来就连成线，基线里也没有 `canvas-connection-target.ts` 这个文件。一旦撤回索引、恢复原控制器扫描，圆周命中与命中顺序随原实现一起恢复；`queryBounds` 的外扩只是让新索引恢复原结果的配套修正，不是独立的产品收益。若后续选择「保留函数提取、只移除索引」，那是另一种具体改动，仍以原基线结果为准，不能为了留下「正确性修复」而强留索引模块。

第四轮只补测量材料，不改变上面的判断。它改变的是「能不能按同条件复放」：两个固定源码现在各自有一份可应用、可复放、共用同一套计数与计时口径的插桩材料（第 5.6 节），正式前后采样的准备缺口不再存在；正式采样仍按第 5.4 节执行。

后续修改需对新固定提交复查，本报告结论不自动外推到修正版。
