## 1. 结论

1. **吸附圆精确相切处会漏接并误开创建菜单**（复查 P2）。已按「只放宽连线粗筛、不动共享空间索引」做最小修复；锁住它的是边界差分（2880 组，旧索引 144 组位置不一致 → 修正版 0）与**真实控制器入口回归**（`web/test/canvas-connection-drop.browser.test.ts`：相切位置连成线、相切外 1 px 打开创建菜单、0.6×/2× 缩放同样如此）。这是第二轮唯一新增的产品行为修正，第三轮没有再动产品代码。
2. **索引改动的收益取决于画布形态**：普通画布热查询变快但幅度很小（300 节点每次省约 0.009 ms），首次建立和更新后重建**更贵**；真实分镜组画布（背板在数组末尾）收益明确（1000 节点首次查询 `3.251 → 0.126 ms`）。
3. 因此结论是**有条件保留**：不以「最坏输入不可达」撤回，也不以热查询倍数当作已解决。
4. **完整 Mac 客户端的帧率定量对比本轮没做**。按约定它要等 #88 重负载结束通知；本轮只把隔离客户端、真实鼠标路径、结果回传通道和夹具准备好，并跑了一次**干跑**（数据在第 5 节，明确标注了混杂因素，不作为 FPS 结论）。第三轮修掉了这批材料里会让正式采样失效的几处工具缺陷（第 0 节末表、第 5.5 节），因此第 5.3 节的干跑数字只能当路径连通性证据，不能当帧率证据。

## 2. 吸附圆精确相切漏判：复现、最小修复、回归

### 复现

目标图片左上角 `(1000, 0)`、尺寸 `320 × 180`，从另一张图片的输出端拖线，100% 缩放，指针在 `(944, 90)`（左输入端外侧 56 px，正好相切）：

| 返回或最终动作 | 基线 | 候选（修复前） |
| --- | --- | --- |
| `nodeId` | `target` | `null` |
| `isNearNode` | `true` | `false` |
| 松手后 | 连成线 | 打开创建菜单 |

复现脚本在 `web/.local/canvas-interaction/repro-tangent.ts`（临时目录，收尾已删）；结论与 #101 的 `hook-browser.json`（36 条真实 hook 路径）一致。

### 根因

查询矩形用吸附圆的外接矩形，而共享空间索引的矩形相交是**严格比较**（`left.right > right.left && left.left < right.right`）。端口锚点落在节点边界上（`position.x` / `position.x + width`），左右相切时节点边界与查询矩形**只共边**，整条被丢弃；后面的精确圆判定（`dx² + dy² <= r²`，闭区间）根本没机会跑。

### 最小修复

`web/src/lib/canvas/canvas-connection-target.ts`：

- 新增 `queryBounds(world, handleRadius)`：查询矩形按 `Math.max(1e-6, |world.x| * 1e-12, |world.y| * 1e-12)` 外扩，让闭区间的边界命中也进入候选；真正命中仍由原来那次精确圆判定决定。
- `snapBounds` 改为 min/max 归一（覆盖负向/零尺寸卡片），保证节点自身边界一定是有效矩形。
- **没有改共享的 `canvas-spatial-index.ts`**：它的严格相交被 `canvas-selection.ts`、`canvas-frame.ts`、`use-canvas-render-model.ts` 的裁剪等调用有意依赖。

### 回归证据

- `web/test/canvas-connection-target.test.ts`（19 条，全过）：精确相切命中、相切内外 0.5 px 分界、相切位置上的非候选节点仍 `isNearNode=true`、容差不把圆外节点带进来。它**只覆盖 resolver 几何**：文件里的「最终动作」是测试内重写的三元表达式，不能当真实松手分支的证据（第 0 节末表）。
- `web/test/canvas-connection-drop.browser.test.ts`（新增，3 条，全过）：装载**真实** `useCanvasConnectionController`，用真实 `pointerdown → pointermove → rAF → pointerup` 走普通与批量两条路径，核对松手后的分支：相切位置连成线且不开创建菜单、相切内 1 px 连线、相切外 1 px 打开创建菜单、0.6× 与 2× 缩放同样如此。把落点模块换成首轮 `f7b82b71` 的索引实现后，相切断言失败（悬停目标从 `target` 变成 `null`）。

### 3.3 怎么读这张表

- **热查询**变快，普通画布幅度很小（300 节点每次约 0.009 ms），真实分组画布幅度大。
- **首次建立**和**更新后重建**更贵：仅变更非几何数据（例如 `taskProgress`）也会换数组、下次查询时重建全量索引。
- 重建是**惰性**的：不是每次进度更新都立刻建索引，停止拖线期间的多次更新可以只在下次查询建一次。所以不能把它说成「陈旧索引缺陷」，也不能把热查询当作完整成本。
- 普通画布上「函数更快」不能单独支持「用户感觉不再卡」；真实分镜组才改变了判断。

### 5.2 排障：本轮主要耗时（重要）

1. **数据目录不能放在外置卷**。重建后 ad-hoc 重签的客户端写 `/Volumes/ExternalWork/...` 被 macOS 权限拦住（TCC 按签名授权），表现是：窗口起得来、前端渲染出启动页，但**后端起不来、不写 `runtime.json`、不监听端口**。把数据目录换到内置盘（`/tmp`）后立刻正常。这是本轮排障花掉最多时间的一条。
2. **后台投递的拖拽在这个 WKWebView 里到不了连线端口**：`delivery_mode` 默认（不前置窗口）时拖拽事件被吞，`落点调用=0`；必须 `delivery_mode: "foreground"`（前置窗口 + 真实指针）才走到连线控制器。
3. 坐标换算：窗口 1440×960 pt，WebView 视口 1440×928 CSS、`dpr=2`；截图 1366 px 宽 → `pt = px × 1440/1366`，`CSS = pt − (0, 32)`。
4. 启动排障：客户端需要 `Contents/Resources/plugin-packages`（否则报「未找到官方插件目录」）。

**混杂因素，必须一起读**：after 那一行跑在一块**已经有 19→20 连线**的画布上（之前探针拖过一次），后续拖线不再产生新连线；before 那一行是**全新画布**，第一次拖线真的新建了一条连线，带来额外的状态更新与渲染。所以 `页面渲染 96 vs 173`、`节点渲染 45 vs 212`、以及 before 的 p95 变差，**不能归给 resolver**。

能被这一轮支持的只有两条：

- 候选侧落点判定在 300 节点上是 `3 ms / 67 次 ≈ 0.045 ms/次`，索引查询 `1 ms / 67 次`，**在 60 fps 的一帧预算里看不到**；
- 真实鼠标拖线路径本身是通的（落点调用 67 次说明端口被命中、控制器被调用），不是合成事件。

**因此本轮不宣称任何 FPS 改善。**

### 5.5 测量材料修正与复放（第三轮）

复查第二轮指出这批材料还不能直接复放同条件对照。本轮修掉下面四处，**产品代码没动**；复放命令与结果在 `verify-tools.py`、`verify-tools.json`（同目录）。

1. **分组种子的连线端点失效**（`seed-canvas.py`）。分组形态的节点 id 是 `perf-child-*`，连线端点却写死 `perf-node-*`，分组画布的 150 条连线**全部指向不存在的节点**；那样的「150 条连线」既不能显示也不能参与规划。改成用真实节点 id 顺序配对，并在写入前自检端点。`python3 seed-canvas.py . --self-check` 现在输出 `invalidEndpoints: 0`（普通 300 节点 150 条、分组 301 节点 150 条）。
   限制：种子只保留「背板追加在数组末尾」这一结构，布局和尺寸没有复用真实的多选创建动作；正式的分组采样优先在客户端里真实多选创建。
2. **帧级标记恒为 0**（`native-probe.patch`）。`dropTargetCallsThisFrame` / `indexBuildsThisFrame` 只有初始化和清零，从不随控制器与落点模块的计数增加，干跑里总调用 22/67/68 而「含落点帧」一直是 0。改成在每帧边界读总量并取差（`previousDropTargetCalls` / `previousIndexBuilds`）。隔离复放（一帧内各加 1）现在输出 `含落点帧=1 含重建帧=1`。
3. **查询计时重复包含建立**。`索引查询耗时` 的起点在 `nodeIndexFor` 之前，等于「建立 + 查询」，不能与 `索引建立耗时` 相加。改成先取索引再计时查询，并新增 `索引合计耗时`。
4. **前后构建来源没有钉选**。归档补丁只在候选快照上验证过 `git apply --check`，没有基线控制器的同口径插桩补丁与完整构建命令，`prepare-native-app.sh` 也不确定源码。现在明确：before 取 `6a155448…`、after 取 `e54d4863…`，两侧用同一份 `native-probe.patch`，构建前记录源码提交、`git status --short`、补丁 sha256 与构建命令。

另外补一条**真实控制器入口**的回归：`web/test/canvas-connection-drop.browser.test.ts`（新增 3 条）装载真实控制器、分发真实 PointerEvent，核对相切位置与相切外 1 px 的松手分支；把落点模块换成首轮索引后该用例失败（第 2 节）。

差分夹具（`canvas-interaction-bench.ts`）同时修了三处：`--boundary` / `--parity` 现在是真开关（不再只影响计时循环，`--nodes` 也真的决定取样规模）；边界取样改用「可连接的源 + 可见且可连接的目标」（`buildBoundaryCanvas`），并输出每个夹具、每个规模的实际命中数；随机取样也补上了批量 resolver。旧索引在同一批 2880 组取样上是 144 组位置不一致、修正版 0，且 `mixed` / `group-late` 的普通与批量命中数都不再是 0。这些结论由 `verify-tools.py` 一次跑完并断言（`verify-tools.json`）。

- **完整客户端帧率定量对比未做**（等重负载结束通知）；第 5.3 节的数据有混杂因素。
- 索引**内存**没做堆快照，不宣称已排除所有内存问题。
- 只测到 `p95` 尾延迟的 1000/5000 分镜组 60 次查询场景只有 12 组配对样本（#101 为控成本），不作可靠尾延迟结论。

## 8. 保留还是撤回

**有条件保留。** 理由与条件：

- 保留的依据：真实可达的分镜组画布上，计入首次建立与更新后重建仍有明确逻辑收益（1000 节点 `3.251 → 0.126 ms`）；相切漏判已修，且有边界差分（旧索引 144 组 → 0）与真实控制器入口回归（`canvas-connection-drop.browser.test.ts`）锁住；索引按数组身份缓存，没有新增需要同步的状态。
- 条件：正式原生采样若显示目标画布没有可见改善、且首次建立/更新后重建带来可见停顿，则应**撤回产品索引改动、只保留研究证据**。也不需要等到「额外出现可见停顿」才考虑撤回：若目标场景既无可见收益、也无独立的必要正确性收益，就不足以为索引复杂度背书。
- **撤回后不需要额外保留相切修复。** 相切漏判是首轮索引引入的回归，原产品基线（`6a155448`）没有这个缺陷：原控制器用 `<=` 的闭区间圆判定，在精确 56 px 处本来就连成线，基线里也没有 `canvas-connection-target.ts` 这个文件。一旦撤回索引、恢复原控制器扫描，圆周命中与命中顺序随原实现一起恢复；`queryBounds` 的外扩只是让新索引恢复原结果的配套修正，不是独立的产品收益。若后续选择「保留函数提取、只移除索引」，那是另一种具体改动，仍以原基线结果为准，不能为了留下「正确性修复」而强留索引模块。

后续修改需对新固定提交复查，本报告结论不自动外推到修正版。
