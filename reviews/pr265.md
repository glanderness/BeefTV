## 必须修复

### 1. P1：Ark 渠道改走插件后丢失已配置的 Seedream 参数

位置：`backend/internal/generation/image.go:24`。[本次提交源码](https://github.com/glanderness/BeefTV/blob/a2fc7be474f5e13b97fc52e212aecc63879d9de9/backend/internal/generation/image.go#L24)

新增的 Ark 排除条件使此前能进入 `runSeedreamImageTask` 的请求改走 `RunDeclarativeProtocolTask`。但 `ProtocolRequestFromInput` 没有传入 `SeedreamMode`、`SeedreamOutputFormat`、`SeedreamOptimize`、`SeedreamWatermark` 等设置，现有 Ark manifest 也没有对应的完整映射。未加载插件时的 `VolcengineArkImageBody` 同样不能保留这些设置。

离线复现使用 `dola-seedream-5-0-pro-260628`、`volcengine-ark-image`、一张合成参考图，并设置图层拆分、JPEG、水印与快速优化。加载仓库真实 Ark manifest，由 `captureImagePort` 拦截请求并返回合成 PNG，没有访问供应商：

| 请求字段 | PR 基线 | PR 最新提交 |
| --- | --- | --- |
| `layer_decomposition` | `true` | 缺失 |
| `output_format` | `jpeg` | 缺失 |
| `watermark` | `true` | `false` |
| `optimize_prompt_options.mode` | `fast` | 缺失 |

这会让用户确认的图层拆分变成普通生图，仍可能产生付费请求；单图的格式、水印等选择也会失效。问题来自执行路径改变，不是尺寸映射本身。

最小修复方向：改走插件前补全上述参数的传递、校验和响应处理，或保留已经支持这些选项的路径。补充从 `RunImageTask` 进入真实 manifest 的回归用例，不能只测 `ProtocolImageAspectRatio` 或请求体 helper。

### 2. P2：尺寸预检误拦合法值，同时放过无效值

位置：`backend/internal/operations/canvas_node_configure.go:175`，尤其第 191 行；调用点包括第 161 行和 `generation_submit.go:190`。[本次提交源码](https://github.com/glanderness/BeefTV/blob/a2fc7be474f5e13b97fc52e212aecc63879d9de9/backend/internal/operations/canvas_node_configure.go#L175)

`isValidSeedreamDraftSize` 对所有型号使用同一档位列表，并要求宽、高各自处于 `1024..4096`。官方限制实际区分型号，并按总像素与宽高比校验；单边范围不能代替它。[火山方舟图片生成 API](https://docs.volcengine.com/docs/ark/image-generation-api?lang=zh&redirect=1)、[BytePlus Seedream 文档](https://docs.byteplus.com/en/docs/modelark/seedream-4-0-5-0?redirect=1)

通过现有 `configureFixture` 调用真实 `opCanvasNodeConfigure`，得到以下结果：

| 型号 | `size` | 应有结果 | PR 实测 |
| --- | --- | --- | --- |
| 4.0 | `1600x600` | 接受 | 拒绝 |
| 4.5 | `5504x3040` | 接受 | 拒绝 |
| 4.5 | `1500x1500` | 拒绝 | 接受 |
| 4.5 | `1K` | 拒绝 | 接受 |
| Pro | `4K` | 拒绝 | 接受 |

`1600x600` 还是仓库现有 `TestSeedreamCustomGatewayKeepsConfiguredVersion` 使用的尺寸。新预检会使原本可以使用的自定义尺寸无法配置或提案；无效值则仍可能到任务执行时才被上游拒绝。[已有测试](https://github.com/glanderness/BeefTV/blob/a2fc7be474f5e13b97fc52e212aecc63879d9de9/backend/internal/generation/image_seedream_test.go#L53)

最小修复方向：按型号共用一份尺寸解析与能力规则，比例先映射为最终尺寸，再检查该型号的档位、总像素与比例；同时供预检与实际请求使用。自定义渠道的能力不能仅凭模型名称套入任意供应商限制。补测 configure、prepare、propose 三个真实入口；新增测试虽然名含 `AndPropose`，实际只调用了 configure。

### 3. P2：国内 Pro / Flash 被错误归入 Lite

位置：`backend/internal/providerpreset/seedream.go:6`。[本次提交源码](https://github.com/glanderness/BeefTV/blob/a2fc7be474f5e13b97fc52e212aecc63879d9de9/backend/internal/providerpreset/seedream.go#L6)

去掉 `doubao-` 后，Pro / Flash 的名称分别成为 `seedream-5-0-pro-*`、`seedream-5-0-flash-*`；现有专属分支仍要求 `dola-seedream-*`，因此两者都会命中通用 `seedream-5-0-*` 并返回 `lite`。离线函数探针确认：

```text
doubao-seedream-5-0-pro-260628   -> lite（应为 pro）
doubao-seedream-5-0-flash-260915 -> lite（应为 flash）
```

这些是官方的 Pro / Flash 型号。[火山官方型号与能力说明](https://docs.volcengine.com/docs/ark/seedream-5-0-pro?lang=zh)

影响不止型号标签：`DefaultImageCapabilityConfig` 会给它们套用 Lite 的分辨率、参考图数量和透明背景能力；通过 `openai-image` 调用时，`seedreamImageBody` 会拒绝本应支持的图层拆分与透明背景，还可能发送错误的组图参数。该 PR 对国内前缀的支持因此不完整。

最小修复方向：先精确识别国内、国际 Pro / Flash，再匹配通用 5.0；补充型号与能力测试。前端 `web/src/lib/seedream-image.ts` 也应同步识别，避免前后端对同一型号给出不同能力。

### 4. P2：旧失败回执会覆盖后来启动的新任务关联

位置：`backend/internal/app/assistant_production_progress.go:85`。[本次提交源码](https://github.com/glanderness/BeefTV/blob/a2fc7be474f5e13b97fc52e212aecc63879d9de9/backend/internal/app/assistant_production_progress.go#L85)

新增写回按旧制作方案找到失败任务后，无条件把节点的 `taskId`、`taskStatus`、`status` 等字段改回旧任务，没有检查节点是否已关联后来启动的任务。`GenerationTargets` 比较生成参数，不比较节点当前的任务身份；`validateProductionTask` 校验的也是旧任务与原方案，不能证明旧任务仍拥有当前节点。

可发生的场景：整片中的图片任务失败，用户在原节点使用相同参数手动重试；旧制作回执仍在等待或扫描，新任务已经关联节点。前端允许已失败任务重新生成，直接生成也不会自动取消旧助手回执。

离线复现沿用 `productionProgressFixture`：将原图片任务置为失败，在隔离测试库创建同画布、同参数的新运行任务，将节点关联新任务，再调用 `ClaimAssistantContinuation`。结果为：

```text
调用前：taskId=new-manual-task, taskStatus=running, status=loading
PR 最新提交调用后：taskId=<旧任务>, taskStatus=failed, status=error
taskClientOperationId 仍是 manual-retry，任务身份字段相互矛盾
PR 基线调用后：保留 new-manual-task / running / loading，claim 返回错误
```

这会使新任务仍在运行时节点却显示旧失败，且节点失去新任务关联。该问题只需正常失败重试和回执扫描交错，不依赖修改生成参数。

最小修复方向：提交失败状态前检查节点仍关联该任务或可核验的原提交身份。发现节点已被新任务接管时，停止旧回执对该节点的写回；保留旧任务失败供原制作流程检查。补充旧任务失败、新任务运行，以及旧任务取消、新任务已成功两种交错用例。
